# v1.4.0 — Async Mirror Writes

## Goal

Per-statement opt-in async mirroring of writes to a *second* helix dual-cluster
pair, used for seamless Cassandra cluster migrations. The mirror is
caller-controlled, bounded with backpressure, durable via the replay system,
and toggleable at runtime.

### Use case

The infra team stands up a new pair of Cassandra clusters as a future home for
the application. For some tables, the application needs ~7 days of write
history mirrored into the new clusters so regression queries can be validated
against the new pair before cutover. Massive time-series tables are excluded
from mirroring and migrated separately via blue/green canary traffic
switching. Mirroring is per-statement: the caller decides which writes to
mirror.

## Non-goals (v1.4.0)

- Mirror reads
- Time-windowed auto-cutover (the 7-day window is operated externally)
- CQL-parsing-driven table selection
- Cross-major-version adapters
- CDC-style change events
- Mixed-policy batches (per-statement-within-a-batch selection)

## Architecture — orthogonal side-channel

```
┌─────────────────────────────────────────────────────────────────┐
│  CQLClient  (current pair: primary + secondary)                  │
│   ├── WriteStrategy (Concurrent / Sync / Adaptive / …)           │
│   └── after Exec returns (any-cluster ack) ─┐                    │
│                                             ▼                    │
│                       MirrorEngine (if Mirror() && enabled)      │
│                       ├── bounded enqueue (drop on full)         │
│                       ├── worker pool                            │
│                       │     └── exec against mirror CQLClient    │
│                       └── on failure → Replayer (separate)       │
└─────────────────────────────────────────────────────────────────┘
```

The `MirrorEngine` is **fully decoupled** from the primary write strategy. It
only consumes the *outcome* of the primary path, never its internals. This is
the design’s most important property:

1. **Conceptual fit.** Mirror is "what to do *after* a write succeeds." Write
   strategy is "how to do the write." Separate axes.
2. **Bug isolation.** AdaptiveDualWrite’s known both-async-fail bug returns
   `DualClusterError` with no replay. Under the orthogonal design, both async
   fails → primary returns error → mirror never fires → no inconsistency.
3. **Operational independence.** Mirror cluster issues should never impact
   the primary path. Separate worker pool, replayer, metrics namespace, and
   logger give clean blast-radius separation.

## Public API

### Wiring (in-process mode)

```go
// 1. Mirror destination is just another CQLClient (its own dual pair).
mirror, _ := helix.NewCQLClient(
    helix.WithPrimary(newClusterA),
    helix.WithSecondary(newClusterB),
    helix.WithWriteStrategy(helix.ConcurrentDualWrite),
    // ... mirror's own logger, metrics, replayer for the new pair itself
)

// 2. Wire it into the main client.
client, _ := helix.NewCQLClient(
    helix.WithPrimary(currentA),
    helix.WithSecondary(currentB),
    helix.WithWriteStrategy(helix.ConcurrentDualWrite),
    helix.WithMirror(mirror,
        helix.WithMirrorQueueSize(8192),
        helix.WithMirrorWorkers(4),
        helix.WithMirrorReplayer(replayer),       // for mirror-write failures
        helix.WithMirrorLogger(mirrorLogger),     // dedicated
        helix.WithMirrorMetrics(mirrorMetrics),   // dedicated
        helix.WithMirrorEnabled(true),            // initial state
        helix.WithMirrorOnDrop(onDropFn),         // optional callback
    ),
)
```

### Per-statement opt-in

```go
err := session.Query("INSERT INTO users …", args).
    Mirror().
    ExecContext(ctx)

err = batch.Mirror().ExecContext(ctx)   // whole-batch
```

`Mirror()` is **always async, fire-and-forget**. The caller never sees mirror
errors. `Mirror()` is the *only* mode in v1.4.0; the name is short because
"async" is the only flavor.

### Runtime control (hot reconfig)

```go
client.Mirror().Enable()
client.Mirror().Disable()      // stop accepting new enqueues; drain in-flight
client.Mirror().Enabled() bool
client.Mirror().Stats() helix.MirrorStats
```

Enable/Disable is the only hot-reconfigurable knob in v1.4.0. Queue size and
worker count are set at construction time.

### NATS publisher mode (out-of-process)

For production migration use cases, the recommended deployment publishes
captured mirror writes to a durable NATS stream and lets a separate worker
binary execute them against the mirror clusters.

```go
// App side — no mirror CQLClient in the app process.
helix.WithMirrorPublisher(natsReplayer)

// Worker side (separate binary).
worker := helix.NewMirrorWorker(natsReplayer, mirrorClient,
    helix.WithMirrorWorkerConcurrency(8),
    helix.WithMirrorWorkerLogger(...),
)
worker.Start(ctx)
```

Both modes share the same `Mirror()` query API, drop callback, metrics shape,
and hot enable/disable surface. The mode is chosen at wiring time.

## Semantics

| Concern | Decision | Rationale |
|---|---|---|
| Trigger condition | Mirror fires when the primary write had **at least one cluster ack** (any-cluster-ack: full or partial success on the current pair) | Matches replay’s "landed somewhere" criterion; if both current clusters failed there is no data to mirror |
| Enqueue backpressure | Non-blocking. Queue full → drop + counter + rate-limited warn log + `WithMirrorOnDrop` callback | The hot path must never stall on mirror |
| Worker failure | Push to replay queue; replay worker retries until success or TTL | Reuses battle-tested replay durability |
| Replayer | Separate instance from the primary client’s replayer | Different SLAs, independent failure domains, no shared queue depth |
| Replayer routing | The `Replayer` is passive transport; the `Worker` binds replay records to the destination `CQLClient`. Mirror engine builds an internal `Worker` pointing at the mirror client. Same `Replayer` *interface* is reused; cross-contamination on shared NATS infra is prevented by distinct streams/subjects per worker | No new replayer type required |
| Disable behavior | Stop accepting new enqueues; drain items already in the queue | Predictable, no abrupt data loss |
| Batch support | `batch.Mirror().ExecContext(ctx)` mirrors the whole batch atomically | Mixed-policy batches out of scope |
| LWT / IF | Mirrored as-is; mirror outcome may diverge (e.g., `IF NOT EXISTS` race). Logged + metric’d, never surfaced to caller | Mirror is best-effort eventually-consistent by design |

## Mode comparison

| Aspect | In-process workers | NATS publisher + external worker |
|---|---|---|
| Durability of captured writes | Lost on app crash unless they reached replay (failure-only) | Durable from the moment `Mirror()` returns |
| App memory pressure | Bounded queue lives in app heap | Tiny publish buffer |
| Mirror cluster outage | Queue fills → drops; long outage = data loss | NATS absorbs hours/days of backlog |
| App restart / deploy | In-flight queue drains or drops | Zero impact |
| Scaling mirror throughput | Bound to app worker count + connections | Independent worker fleet |
| App contention with mirror | Yes — CPU, conns, latency | None |
| Multi-app consolidation | Per-app queue | Single shared worker fleet |
| Latency: `Mirror()` → mirror cluster | Lower (in-memory hop) | Higher (sub-ms NATS hop) |
| Operational complexity | Lower | Higher (separate binary) |
| Infra requirement | None | NATS JetStream |
| Fits 7-day migration use case | Acceptable | **Recommended** |

For the migration use case, NATS-publisher mode is the recommended production
deployment. In-process is retained for dev/test/local and small deployments.

## Logging

Dedicated `helix.mirror` logger, same shape as the existing
`AdaptiveDualWrite` logger. Key events: enqueue dropped (rate-limited),
write error, replay enqueue, enable/disable transitions.

## Contract clarifications

These items sharpen the contract without changing the architecture. They were
identified during design review and must hold in the implementation.

### Timestamp preservation (parity-critical)

Mirror writes execute later than the primary write — by milliseconds in the
hot path, by minutes-to-hours on the replay path. Server-side timestamps
must match the primary write or `WRITETIME(col)`-aware regression queries
will diverge in the mirror cluster.

- **Capture:** at `Mirror()` opt-in time (synchronously before primary
  `Exec` returns), the engine records a client timestamp in microseconds
  (matching existing `types.ReplayPayload.Timestamp` convention).
- **Apply:** the mirror executor uses
  `session.Query(...).WithTimestamp(captured).ExecContext(ctx)` — the same
  pattern the primary replay path already uses
  (`CQLClient.DefaultExecuteFunc`, `cql_client.go:974`).
- **Result:** mirror writes land at the mirror cluster with the original
  server-side timestamp. LWW, TTL, tombstone, and `WRITETIME` semantics
  match the primary cluster.
- **Reuse `types.ReplayPayload`** as the capture struct verbatim. No new
  type required. `TargetCluster` is set by the mirror engine when
  enqueueing per-cluster work for the mirror dual pair.

### Bound-value capture

`[]any` args may be backed by pooled buffers or slices the caller mutates
after `Exec` returns. Mirror executes on a different goroutine — even on
the in-memory hop — so it must not observe caller-side mutation.

- The engine performs a **deep copy** of the arg slice and any
  `[]byte`/non-trivially-copyable elements **synchronously before
  `Exec()` returns** to the caller. This cost is on the caller's hot path
  and is the only correct option.
- Same rule applies to `BatchStatement.Args` for batched mirroring.
- (The existing replay path has the same theoretical concern but is less
  acute because replay only fires on primary failure. Mirror fires on
  success and is therefore the common case.)

### Publisher-mode backpressure

When `WithMirrorPublisher(replayer)` is configured and the underlying
publish fails (NATS unreachable, JetStream stream unavailable):

- Maintain a small in-memory ring buffer (default 1024, configurable) in
  front of the publisher.
- If publish fails, captures land in the buffer; a background goroutine
  drains the buffer with retry/backoff.
- If the buffer fills, behave identically to in-process drop semantics:
  increment `helix.mirror.publish.dropped`, rate-limited warn log,
  invoke `WithMirrorOnDrop` callback.
- The hot path **never blocks** on NATS publish. Publish-with-ack is
  done by the background drainer, not the caller.

### Trigger condition — known parity hole

Mirror fires when the primary `Exec` returns with at least one cluster
ack. Writes that succeed only via the *primary's* replay path (i.e., both
current clusters initially failed, primary returned an error, primary
replay later landed the write) are **not** mirrored.

- For the 7-day regression-query use case this is acceptable: it's a
  rare path and a small fraction of writes.
- Documented as a known parity gap in `docs/mirror.md`.
- An explicit hook on primary-replay success that re-feeds the mirror is
  deferred past v1.4.0 (out of scope; can be added without API change).

### Worker context

Mirror workers (in-process and external) must execute with the
engine's/worker's own background context, **not** the caller's
`ExecContext` ctx. The caller's ctx may be canceled before the mirror
runs — especially after replay delays.

### Disable / Enable semantics

- `Disable()`: stop accepting new enqueues; in-flight queue items
  continue to drain via existing workers.
- `Enable()` while a drain is in progress: **resume normal operation**.
  Items still in the queue continue draining; new enqueues are accepted
  again immediately.
- These transitions are atomic; tests must cover the `Disable→Enable`
  race during drain.

### Idempotence requirement (caller responsibility)

Mirror writes may be retried by the worker's replayer. Callers using
`Mirror()` should ensure mirrored statements are idempotent or accept
divergence. Specifically:

- **Counter updates** are not idempotent under retry → divergence.
- **LWT (`IF` clauses)** may have differing outcomes on the mirror
  cluster (a `IF NOT EXISTS` race resolves independently).
- **Read-modify-write** patterns built on application-side reads may
  diverge.

Mirror logs and metric'd these as warnings; never surfaces to the caller.

### Operational notes

- **Schema superset:** the mirror destination must contain a superset of
  any mirrored statement's referenced keyspaces, tables, and columns.
  Mismatch → mirror writes fail and accumulate in replay. Validate
  before enabling.
- **Cross-instance ordering (publisher mode):** multiple app instances
  publishing to the same NATS stream provide no global order. Dependent
  writes on the same partition key from different instances may apply
  out of order at the mirror cluster. Acceptable for the migration use
  case (partition-key writes are typically idempotent or LWW-resolved
  via timestamp).

## Implementation phases

1. **Core engine (in-process)**
   - `MirrorEngine`, `WithMirror`, `Mirror()` query/batch method
   - Bounded queue + drop policy + `WithMirrorOnDrop`
   - Worker pool → mirror `CQLClient`
   - Hot enable/disable, drain-on-disable
   - `client.Mirror()` controller (Enable/Disable/Enabled/Stats)
   - Unit tests: enqueue, drop, enable/disable, batch path
2. **Replay durability for mirror failures**
   - Internal `Worker` binding `Replayer` → mirror client
   - `WithMirrorReplayer`
   - Tests: failure → replay → eventual success
3. **NATS publisher mode**
   - `WithMirrorPublisher(replayer)` — bypasses in-memory queue
   - `helix.NewMirrorWorker(...)` — external consumer
   - Tests: end-to-end publish → external worker → mirror cluster
4. **Metrics & dedicated logger**
5. **Docs & integration tests**
   - `docs/mirror.md` user guide
   - Migration recipe in README/examples
   - Real-Cassandra integration tests with failure injection (mirror down,
     slow, partitioned)
