# v1.9.0 — Iterator First Page on a Read Leg

## Summary

`(*cqlQuery).IterContext` (query.go:291) hands the caller's context straight to the driver
and never passes through `attemptRead` (read_path.go:517),
so a dual-cluster client configured with `WithClusterReadTimeout(d)` gets no leg deadline,
no attribution, and no failover for the page the driver fetches synchronously inside `IterContext`.
This plan bounds that first page by `d`, counts an expiry against the cluster that owns it,
and re-fetches the first page on the other cluster when the failover gating allows it.
Later pages keep today's behaviour: the driver's auto-paging under the caller's context, reported at `Close`.
The mechanism is a custom `context.Context` inside the root package that delegates `Deadline()` and `Value()` to the caller,
latches one terminal error, and closes its own `Done` channel when the leg timer expires while armed,
when the caller's context ends, or when the iterator is finished with.
There is no public API change, no `adapter/cql` interface change, and no driver fork change,
and everything is gated on `ClusterReadTimeout > 0 && !IsSingleCluster()`,
the predicate `readLegContext` (read_path.go:500) already uses,
so a single-cluster client and the default configuration keep running exactly the code they run today.

## Motivation

`tmp/fdc-1.8.1-feedback/helix-improvements.md` §0 measures the two read paths of a caller
whose preferred cluster is frozen with `docker pause` (socket open, no answers),
under `Timeout=5s`, `WithClusterReadTimeout(1s)`, sticky read and a latency circuit breaker:

| path | preferred cluster frozen | recovery |
|---|---|---|
| `Query.ScanContext` | leg expires at 1s, `ErrClusterTimeout`, failover on the third read | ≈3s |
| `Query.IterContext` | no leg deadline; the error surfaces only after the caller's own budget ends | ≈33s, ≈65s with the production `Timeout=10s` |

The causal chain is short.
Without a leg deadline the driver call returns only when the caller's context expires,
`cqlIter.Close` classifies with that same context (iter.go:45 → `classifyReadErr`, read_path.go:46),
the outcome lands in `readCtxErr`, and `iterClosed` (health.go:133) records nothing:
no session stats, no `RecordFailure`, no `OnFailure`.
The breaker never opens and the sticky preference never moves,
so every later read repeats the wait until gocql's own heartbeat marks the host down.
The caller in question reads exclusively through `IterContext`, so its whole read surface has this shape.
`ScanContext` already has the rules that fix it; the first page of an iterator simply never entered them.

## Design

### Mechanism

Both adapters fetch the first page synchronously inside `IterContext`
(v1 `adapter.go:339` → `q.query.WithContext(ctx).Iter()`, gocql `session.go:1309`;
v2 `adapter.go:362` → `q.query.IterContext(ctx)`),
and both drivers keep that same context object for every later page and for the prefetch goroutine
(gocql copies the query in `WithContext`, `session.go:1099`, and `nextIter.fetch` reads `n.qry.Context()`,
`session.go:1719`; the fork does the same at `session.go:2267`).
One object therefore covers the first page and all the rest, and Helix cannot swap it afterwards —
which is why the leg deadline is carried by the context itself
rather than by a `context.WithTimeout` child that would also bound the pages the caller drains.

`firstPageCtx` is an unexported type in the root package implementing `context.Context`:

- `Deadline()` delegates to the caller's context and never advertises the leg deadline.
  The fork consults `ctx.Deadline()` before arming its connection request timer (`conn.go:1606-1611`),
  so delegation keeps that behaviour byte-identical to today.
- `Done()` returns one channel for the lifetime of the context.
- `Err()` returns the latched terminal error when there is one, otherwise the caller's `Err()`.
  Both drivers return `ctx.Err()` verbatim when they wake on `ctx.Done()` (fork `conn.go:1682-1687`).
- `Value()` delegates to the caller's context.

### State machine

```go
type firstPageCtx struct {
    parent     context.Context
    done       chan struct{}
    stopParent func() bool // context.AfterFunc's stop
    mu         sync.Mutex
    timer      *time.Timer
    armed      bool
    expired    bool  // the leg timer latched, with the caller still live
    finalErr   error // latched once; nil while the context follows the caller
}
```

`newFirstPageCtx(parent, d)` returns an armed context:
it creates `done`, sets `armed`, starts `timer = time.AfterFunc(d, fp.legExpired)`,
and registers `stopParent = context.AfterFunc(parent, fp.callerEnded)` (go.mod is `go 1.26.0`).

Three events end the context, all through one latch:

```go
func (fp *firstPageCtx) latch(err error, fromTimer bool) {
    fp.mu.Lock()
    if fp.finalErr != nil || (fromTimer && !fp.armed) {
        fp.mu.Unlock()
        return
    }
    if perr := fp.parent.Err(); perr != nil { // the caller got there first
        err, fromTimer = perr, false
    }
    fp.finalErr, fp.expired, fp.armed = err, fromTimer, false
    fp.timer.Stop() // a terminal context must not be held alive by a pending callback
    fp.mu.Unlock()
    close(fp.done)
}
```

- `legExpired` (the leg timer) calls `latch(context.DeadlineExceeded, true)`.
- `callerEnded` (the parent registration) calls `latch(fp.parent.Err(), false)`.
- `finish()` — terminal cleanup, run once per iterator — calls `latch(context.Canceled, false)`
  and then `stopParent()`.
- `disarm() bool` takes `mu`, clears `armed`, calls `timer.Stop()`, and returns `!expired`:
  true when the leg did not expire, false when the timer latched first.
  Both `latch` and `disarm` stop the timer, so a caller that cancels early does not leave it
  holding this context for the rest of `d`.

Race freedom.
`latch` is the only writer of `finalErr`, `expired` and `done`, it decides under `mu`,
and the one caller that finds `finalErr == nil` is the one that closes the channel,
so the close runs once and publishes fields already written.
`Err()` never changes once non-nil: before any latch it returns the caller's `Err()`, itself stable once non-nil,
and a latch taken while the caller is already done copies that same error instead of claiming a leg timeout —
which is what keeps a cancellation from being followed by a `context.DeadlineExceeded`.
`disarm` and `legExpired` both take `mu`, so exactly one sees `armed == true`:
if the timer wins, `expired` is set and `disarm` reports the loss;
if `disarm` wins, `timer.Stop()` may return false because the callback is already running,
but that callback then finds `armed == false` and returns without latching.
A caller that cancels while armed latches its own error through the parent registration,
`disarm` still reports a win, and the iterator is handed over exactly as today.

`finish()` cancels before it detaches, and that order is what makes cleanup safe:
the driver still holds this context for a prefetch it may have started
(gocql `session.go:1708-1722`, fork `session.go:2240-2247` starting it and `session.go:2267` reusing the context),
and with a caller-supplied deadline
the fork does not arm its request timer at all (`conn.go:1606-1611`),
so merely detaching would leave that fetch with no cancellation source until the connection is torn down.
`cqlIter` runs `finish()` under a `sync.Once` from `closeAndReport` (iter.go:43),
after `i.iter.Close()` has returned the driver's terminal error, so cleanup can never turn a clean close into an error;
`cqlScanner.Err()` (iter.go:161-175) runs the same once, because the `Scanner` contract says
`Err` releases resources and the iterator is not used directly afterwards (cql_session.go:704-706, 768-770).
Detaching matters because a live registration is not always free: `context.AfterFunc` registers with the parent
when it is a standard cancellable context or one implementing `AfterFunc`,
and otherwise starts a goroutine waiting on the parent or on this context's `Done` (`context/context.go:521-528`).
The guarantee is therefore path-scoped, and the plan claims no more than it can hold:
every path reaching `Close()` or `Scanner.Err()` releases the registration whichever way the disarm went,
and the `errorIter` returns for a closed client or a `resolveReadTarget` error never build a context at all.
An iterator the caller abandons keeps its registration until the caller's context ends —
one parked goroutine when the parent is non-standard — which is the same abandonment that already
leaks the driver's own iterator, so "always call `Close`" stays the documented contract
rather than a promise Helix can keep on the caller's behalf.

### Flow in `IterContext`

`legTimeoutActive() bool` (`ClusterReadTimeout > 0 && !IsSingleCluster()`) becomes a small method
called by both `readLegContext` (read_path.go:501) and `IterContext`, so the two gates cannot drift.
When it is false, `IterContext` runs today's body unchanged: no custom context, no timer, no metric.

When it is true:

1. `resolveReadTarget` as today (query.go:295).
   The closed-client and `rt.err` paths return `errorIter` before anything is armed.
2. Build the driver query from the selected holder exactly as today
   (`holder.s.Query(q.statement, q.values...)` then `q.applyConfig(query)`, query.go:296-298),
   build a `firstPageCtx`, call `query.IterContext(fpCtx)`,
   measure `elapsed` as `time.Since(start).Seconds()`, then `disarm()`.
3. Record `IncReadTotal(cluster)` and `ObserveReadDuration(cluster, elapsed)` for the attempt,
   win or lose, exactly where `attemptRead` records them (read_path.go:532-534).
   This refines the "on success" wording of the source notes: a failover counts two `read_total`,
   two `read_duration` and one `read_error`, which is Scan's shape.
4. `disarm` won → return the `cqlIter` as today (`cluster`, `holder`, `overrideActive`, `ctx` = the caller's),
   with the `firstPageCtx` stored on it so `Close` can finish it.
   No `readSucceeded`: `Close` keeps the `iterClosed` reporting, and adding `RecordLatency` here
   would be erased by the `RecordSuccess` that `Close` issues (health.go:89, health.go:133).
5. `disarm` lost → the leg is a Helix timeout:
   - `driverIter.Close()` and discard it immediately (v1 nils the framer, v2 returns the pooled framer),
     then `fpCtx.finish()`. Its close error is dropped — the leg outcome is known
     and the iterator is never handed out, so it is never scanned after disposal.
   - When the caller's context is already done (`ctx.Err() != nil`), the failure belongs to the caller,
     as `clusterTimeoutIfExpired`'s `parent.Err() == nil` guard (health.go:209) and `classifyReadErr` both rule:
     return `&errorIter{err: ctx.Err()}` with no health report and no failover.
   - Otherwise `err = fmt.Errorf("%w: %w", types.ErrClusterTimeout, context.DeadlineExceeded)`.
     `clusterTimeoutIfExpired` itself does not fit — it wraps an error the driver returned,
     and a driver handing back an iterator returns none — but the composed error has the shape it would produce.
   - `health.readFailed(holder, cluster, readClusterErr, err)` (metric, session stats, `RecordFailure`).
   - A query carrying a `PageState` (`q.pageState != nil`) stops here and returns `&errorIter{err}`:
     a paging cursor is only meaningful on the cluster that issued it,
     the same rule `executeReadNoFailover` (read_path.go:613) encodes for slice reads.
   - Otherwise consult the failover gating below.
6. Failover attempt: `announceFailover(selected, fallback, err)`, then one more armed leg on the alternative —
   its own query rebuilt from the alternative's holder through the same `applyConfig`,
   its own `firstPageCtx` with the same `d`, its own metrics and `disarm` —
   mirroring how `tryFallbackCluster` gives the failover leg an `attemptRead` of its own (read_path.go:745).
   Success returns a `cqlIter` whose `cluster` and `holder` are the alternative's,
   so `PageState()` encodes the alternative (iter.go:130) and `Close` reports to it;
   the failed leg was reported against the holder it used and `closeAndReport` uses the iterator's own holder,
   so the two legs' session stats never mix (health.go:22-26).
   `overrideActive` stays `rt.snap.active`: it describes the request, not the cluster,
   and it is what keeps `Close` from reporting to a frozen strategy.
   Failure records `readFailed` for the alternative and returns
   `&errorIter{err: dualReadError(selected, primaryErr, altErr)}`;
   an alternative leg losing its disarm under a dead caller context returns `&errorIter{ctx.Err()}`
   with no health report, mirroring the `!kind.isHealthSignal()` branch of `tryFallbackCluster`.
7. `Query.Iter()` (query.go:268) reaches all of this through `q.getContext()` and needs no change.
   `Batch.IterContext` is a write-path entry point and is untouched.

### Reusing the failover gating

Extraction only; `executeRead` (read_path.go:557-600) keeps its two branches and its two callees keep their names.

| new function | extracted verbatim from |
|---|---|
| `overrideFailoverTarget(ctx, rt, primaryErr) (ClusterID, bool)` | read_path.go:656-672 — empty or self-referencing fallback, `ShouldFailover`, dead caller context |
| `normalFailoverTarget(ctx, selected, primaryErr) (ClusterID, bool)` | read_path.go:685-716 — `ShouldFailover`, then `ReadStrategy.OnFailure` or the plain alternative, then the drain check re-read from `getDrainStates`, then the dead-caller guard |
| `failoverTarget(ctx, rt, selected, primaryErr)` | the `rt.snap.active` branch at read_path.go:594-597; the iterator path calls this one |
| `announceFailover(selected, fallback, primaryErr)` | read_path.go:733-746 — `IncFailoverTotal`, `Warn`, `EventFailover` |
| `dualReadError(selected, primaryErr, altErr) error` | read_path.go:763-767 — the ordered `types.DualClusterError` |

`OnFailure` keeps its position after `ShouldFailover` and before the drain check,
so the sticky preference moves under exactly today's conditions.

`executeOverrideFailover` and `executeNormalFailover` shrink to their target call plus `tryFallbackCluster`,
which itself calls `announceFailover` and `dualReadError`;
no caller of `executeRead`, `executeReadNoFailover` or `executeFallbackRead` changes.
Folding the two into one `executeFailover` is more churn and touches `executeRead`; not proposed.

### Reporting rules

One `IncReadTotal` and one `ObserveReadDuration` per armed leg attempt, whatever its outcome —
`attemptRead` counts a cancelled attempt too (read_path.go:526-535), and this path matches it.
`IncReadError`, the session stats and `RecordFailure` are reported only for a leg that expired with a live caller,
through `readFailed`; a caller cancellation reports none of them and no failover follows.
No `RecordLatency` for a first page, and no new metric or event kind:
`circuit_breaker_open`, `read_route_changed` and `failover` keep coming from `readFailed`,
the strategy transition inside `normalFailoverTarget`, and `announceFailover`.
An `errorIter` reports nothing at `Close`, so each leg is reported exactly once whichever branch is taken.
The existing asymmetry stays: an iterator whose error surfaces at `Close` still records no `IncReadError`
(`iterClosed` never touches the metric, health.go:133-162), only a leg timeout does.

## Tests

### `firstPageCtx`

The unit tests drive `legExpired`, `callerEnded` and `finish` directly rather than waiting on wall-clock timers,
so every ordering is deterministic; `-race` supplements them and does not stand in for them.

- `Deadline()` returns the caller's deadline while armed and `ok == false` for a caller without one;
  `Value()` delegates; `Done()` returns the same channel in every state.
- Timer first: `legExpired`, then `disarm()` reports the loss, `Done()` is closed, `Err()` is `context.DeadlineExceeded`,
  and a second `disarm()` still reports the loss.
- Disarm first: `disarm()` reports the win, `Done()` stays open, `Err()` stays nil,
  and a later `legExpired` — the callback that was already running when `disarm` took the mutex — changes nothing.
- Caller first: cancel the parent, run `callerEnded`, then `disarm()` reports a win and `Err()` is the caller's error,
  which a subsequent `legExpired` does not change.
- The contended schedule the drivers can produce: cancel the parent but run `legExpired` before `callerEnded`.
  `Err()` must be the caller's error, never `context.DeadlineExceeded`,
  and identical on every read taken before and after each callback.
- `finish()` closes `Done()`, latches `context.Canceled`, and detaches: cancelling the caller afterwards changes nothing,
  a second `finish()` is a no-op, and a `finish()` after an expiry or a cancellation keeps the earlier error.
- A custom parent that is neither a standard cancellable context nor an `afterFuncer`
  still propagates cancellation and is still detached by `finish()`.
- An abandoned context — no `finish()` — with a standard cancellable parent:
  cancelling the parent releases the registration and closes `Done()`
  (the provable half; the non-standard parent's parked goroutine is a known limit).
- `var _ context.Context = (*firstPageCtx)(nil)` lives in the test file, per the public-package rule.

### `IterContext` with mock sessions

Two mock shapes carry these: one whose `IterContext` blocks on `ctx.Done()` before returning (the first page hangs),
and one that waits for `ctx.Done()` and then returns a healthy iterator
(the driver answers after the leg expired — the handoff race, made deterministic).
`newMockSession` supplies the healthy alternative, and every client sets `WithClusterReadTimeout(d)` with a small `d`.

- Failover refused by a `ShouldFailover` returning false: `Close()` returns `ErrClusterTimeout`,
  one `IncReadError` and one `RecordFailure` on the selected cluster, `consecutiveFailures == 1`,
  the alternative untouched, `PageState()` nil.
- Failover allowed: rows come from the alternative, the iterator's cluster and holder are the alternative's,
  `PageState()` decodes to the alternative, `Close()` reports `OnSuccess` / `RecordSuccess` to it,
  and `IncFailoverTotal` plus one `EventFailover` were emitted.
  The alternative's query carries the same statement, values, consistency, serial consistency and page size.
- The handoff race: the driver's iterator arrives after the expiry, is closed exactly once,
  is never scanned and never handed to the caller; the read still fails over and the leg is reported once.
- Both legs expire: `Close()` returns a `*types.DualClusterError` with both errors in cluster order.
- A query carrying a `PageState`: `Close()` returns `ErrClusterTimeout`, the alternative is never contacted,
  and the failure is still recorded — for an encoded token naming either cluster and for a raw driver token.
- An `AllowedClusters` override listing both clusters fails over to the snapshot's fallback
  and reports nothing to the frozen strategy at `Close`; an override fencing the alternative off
  produces `ErrClusterTimeout` with no second attempt.
- The caller cancels while the first page hangs: `Close()` returns the caller's error,
  the attempt records one `read_total` and one `read_duration`, and nothing else —
  no `read_error`, no stats, no `RecordFailure`, no failover.
- Metrics per attempt: a successful first page counts one of each; a failover counts two of each and one `read_error`;
  `RecordLatency` is never called on any path.
- A first page that answers: later `Scan` and `Close` behave as today, `Close` reports once, a second `Close` adds nothing,
  a page served from the retained context after `d` has passed still returns rows,
  and a caller cancellation after the handoff still reaches the driver.
- A consumer that only calls `Scanner().Err()` detaches the parent registration once
  and reports to the hub exactly what it reports today (nothing).
- The structural no-op: with `d == 0` in dual-cluster mode and in single-cluster mode with `d > 0`,
  the mock receives the caller's context object itself (pointer identity) and no attempt metric is recorded.
- A closed client and a `resolveReadTarget` error return their `errorIter` with no timer started;
  a holder swapped between the attempt and `Close` leaves the observations on the holder the leg used.
- One table-driven test records the full gating sequence
  (`readFailed`, `ShouldFailover`, `OnFailure`, drain check, `announceFailover`, alternative attempt)
  for a Scan and for an iterator and asserts the same order for both,
  including a refusing policy, a draining alternative, both clusters draining,
  and a caller context that ends inside a policy callback.

Call `ensureReachable(t, a, d)` and `ensureReachable(t, b, d)` before anything else, as `sticky_read_test.go:41-44` does:
a previous scenario's pause can leave the v2 driver with an empty pool that fails every request (`setup_test.go:213-237`).
`withRestoredCluster(t, a)` stays, for pause recovery between scenarios.
Then warm the exact statement on both clusters through `d.wrap(a)` and `d.wrap(b)` directly —
they wrap the sessions the client is built from, one ordinary client read warms only the selected cluster,
and `ensureReachable` prepares `system.local`, not this statement.
Then pause A and loop `IterContext` reads with a 15s caller budget, timing each one.

Ordering the assertions must respect: `readFailed` records the policy failure before the failover branch is entered
(read_path.go:586-597), and `RecordFailure` opens the breaker at the threshold
(`policy/failover_policy.go:531-541`), which `ShouldFailover` then observes (`policy/failover_policy.go:475-481`,
delegated by `policy/latency_circuit_breaker.go:377-382`).
With threshold 3, reads one and two record a failure and return `ErrClusterTimeout` with no failover,
and read three opens the breaker, moves the preference, and is served by B within the same read.
The loop therefore tolerates errors and the bound covers the sequence, not the first read.

- Within 15s a read returns rows served by B (`require.Eventually` driving the loop).
- `circuit_breaker_open` and `read_route_changed` were both emitted.
- Every individual read took less than `d` plus slack (`3*d`), asserted as a bound, never as `2*d` exactly.
- After the switch a read is fast and `mc.GetTotalFailovers()` has advanced;
  route veto is off by default, so the move is the strategy's, not an eligibility filter's.

## Docs and changelog

- `WithClusterReadTimeout` (config.go:1366-1371): the sentence
  "nor to an iterator obtained from Query.Iter, which the caller drains outside any leg" is replaced by
  the new contract — the page fetched inside `IterContext` is a leg like any other
  (bounded by `d`, counted against its cluster, eligible for one attempt on the alternative),
  the pages the caller drains afterwards run on the caller's context and are reported at `Close`,
  and a read carrying a `PageState` never moves cluster.
- `Query.Iter` / `Query.IterContext` Godoc (cql_session.go:292-308) and `(*cqlQuery).IterContext` (query.go:272-290):

## Known limits

- Cold statements: the fork prepares under the connection's context, not the request's
  (`conn.go:1760-1762`, "use connection context ... even if the caller's context is canceled"),
  so the first execution of a statement against a frozen host still waits `Session.Timeout`.
  Warm statements, which is where the traffic is, get the leg deadline.
- Non-timeout first-page errors keep today's shape: the driver hands back an iterator that fails at `Close`,
  which counts there and is not retried. Mid-stream pages likewise keep the caller's attribution.
- A caller that abandons an iterator without `Close` or `Scanner.Err` keeps its parent registration
  until the caller's context ends, and with a parent that is neither a standard cancellable context
  nor an `afterFuncer` that registration is a parked goroutine.
  It is the same abandonment that already skips the health report and leaves the driver's iterator open.
- A driver that wakes on `ctx.Done()` does not release its stream, so a long freeze consumes streams
  until the connection is torn down. `ScanContext` has this today; the e2e scenario is the place to watch for `ErrNoStreams`.
