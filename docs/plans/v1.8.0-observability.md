# v1.8.0 Phase 5 — Observability

Working plan for the Phase 5 items in
[`roadmap.md`](roadmap.md#phase-5--observability-v180).
The roadmap table and the Design Decisions section are binding;
this file fixes the order, the mechanism, and the verification for each item.
Finding IDs stay in the roadmap;
nothing below is quoted into code or commits.

## Scope and process

- Branch `feat/observability` from `main` (`86f0ac1`, Phase 4 merged through PR #10).
  One commit per roadmap item, in the order below.
- `v1.8.0` is tagged after this PR merges.
- Every item: write the regression test first, then make it pass.
  Before each commit: `make lint`, `make test-unit`, `/simplify`.
  Run `go test ./test/integration/` before every push that changes behaviour;
  run `make test-e2e` once before the PR is opened.
- `CHANGELOG.md` `[Unreleased]` gains one entry per observable change.
  Every item here is additive (a new optional collector interface, a new series, a new event kind, or documentation),
  so no default moves and no restore option is needed.
- External review (Codex, root-client and policy/replay reviewers in parallel, each with its own report path)
  before the PR is opened, looping until both report nothing.

## Compatibility rule for this phase

No method is added to `types.MetricsCollector` or to any existing optional collector interface;
a collector that implements one of those today keeps compiling.
Each new signal is a new optional interface resolved by a one-shot type assertion, as the existing eight are.
New event kinds are appended to the kind list and to `docs/cluster-events.md`;
a handler that switches on the kind and ignores unknown values keeps working.

## Items

### 5.1 Preferred-cluster gauge and route-change event

Today the read strategies have no metrics, logger, or event emitter;
`StickyRead.Preferred` is a method on the concrete type and nothing reports a move.

- New optional collector interface `types.ReadRouteMetrics` with
  `SetReadPreferred(cluster ClusterID, preferred bool)`,
  series `{prefix}_read_preferred{cluster}` (1 for the cluster the strategy currently prefers, 0 for the other).
  The strategy calls it for both clusters on every move and once when the collector is installed,
  so the gauge is right from startup.
- New event kind `types.EventReadRouteChanged` (`read_route_changed`) with
  `FromCluster`, `ToCluster`, `Cluster` (= `ToCluster`) and `Reason`.
  Reasons: `"failover"` (the preferred cluster failed and the alternative took over),
  `"alternative known good"` (the cooldown swap),
  `"manual"` (`SetPreferred`, `Reset`),
  `"recovered"` (`PrimaryOnlyRead` returning to A after a successful read or probe).
- Every transition is decided, applied, and enqueued to the outbox
  while the strategy's transition mutex is held, so event order and state order are one order.
  The gauge is written after the mutex is released by a single-owner reconciliation loop
  (the discipline the outbox drain uses): the caller that wins a reporting flag marks the state clean,
  rereads the current preference, writes it, and repeats while a transition marked the state dirty meanwhile;
  every other caller marks the state dirty and returns.
  A collector that blocks therefore holds only the owner, a newer transition completes at once,
  the owner's next write carries the newest state, and a collector that calls back into the strategy
  enqueues and returns without deadlock.
  The outbox drains last, as the breaker does.
  `StickyRead` reads `preferred` again under `mu` and returns without a transition when nothing changes
  (a second concurrent failure on the same preferred, `SetPreferred` of the current cluster, a `Reset` to the current one).
  `PrimaryOnlyRead` gains a transition mutex taken by `OnFailure`, `OnSuccess`, and `Reset`;
  `Select` stays lock-free on the atomics it reads today.
  Recovery through `OnSuccess(A)` and the operator's `Reset` share the state change but not the reason.
- `StickyRead` and `PrimaryOnlyRead` implement `helix.Instrumentable` and `helix.EventEmitterSetter`
  through the existing policy outbox;
  `RoundRobinRead` has no route state and implements neither.
- Root wiring: `autoInjectMetricsAndLogger` and `autoInjectEventEmitter` also visit `ClientConfig.ReadStrategy`;
  `orderedClusterEventKinds` and the reachability switch classify the kind
  (unreachable in single-cluster mode or when the read strategy reports no route).
- The gauge reports the strategy's preference only.
  A route the client overrides for one request (a veto, drain, `AllowedClusters`) does not move it;
  `docs/cluster-events.md` and `docs/strategy-policy.md` say so.

Verification: policy tests for every reason on both strategies (event fields, gauge values);
gated concurrent tests (two failures racing on the same preferred, `OnSuccess` racing `OnFailure` on `PrimaryOnlyRead`)
asserting one event per real transition, in transition order, and the final gauge equal to the final state;
a gated blocking-collector test proving a newer transition completes while an older report is stuck
and the final gauge equals the final state;
no-op tests for `SetPreferred(current)` and an idle `Reset`;
a root test that the read strategy receives the collector and the emitter and that the kind is classified;
`docs/cluster-events.md` event table and kind count updated.

### 5.2 Reserved event admission and outbox drops

Today every kind shares one 128-slot buffer with drop-newest,
so a read-rate flood of `failover` can evict a `circuit_breaker_open` that arrives a microsecond later,
and the policy outbox's own drop counter is never read.

- The dispatcher keeps one FIFO buffer, grown from 128 to 160 slots, and reserves admission:
  a per-operation kind (`failover`, `read_divergence`, `replay_dropped`, `mirror_replay_dropped`)
  is admitted only while fewer than 128 per-operation events are waiting;
  every other kind (state transitions and `read_route_changed`) is admitted while any slot is free.
  A flood of per-operation events therefore leaves 32 slots that only transitions can fill.
  Delivery order stays enqueue order, so the documented contract
  ("independent producers are delivered in enqueue order, with no cross-kind causal guarantee") is unchanged
  and the item stays additive.
  Drop-newest and the single dropped total are unchanged; the kind classification is an exhaustive switch.
- New optional interface `types.ClusterEventDropReporter` with `NoteClusterEventsDropped(n int)`;
  the root dispatcher implements it (an atomic add on its existing counter).
- The outbox never calls the reporter under a policy lock.
  `enqueue` only counts; the drainer, after the policy mutex is released, forwards the unreported count
  to the reporter it finds on the emitter installed at that moment.
  When no emitter is installed the count is retained and forwarded by the first drain after one is installed,
  so a drop is never lost, only attributed to the reporter present when it is forwarded.
  A panicking reporter is recovered and its batch is not counted again.
- `docs/cluster-events.md`: per-operation kinds section lists all four,
  delivery semantics describe the reserved admission, and the drop section says policy-side drops are counted.

Verification: a dispatcher test that floods per-operation events and still admits and delivers a transition
in enqueue order relative to the events admitted around it;
a test that the per-operation count never exceeds its share and that transitions fill the whole buffer alone;
an outbox test that an overflow, an emitter removal mid-flight, and an emitter panic each reach a reporter exactly once,
including the removal case where the report arrives after a new emitter is installed;
a reentrant reporter test (the reporter calls back into the policy) that does not deadlock;
a stop-while-emitting test;
the existing ordering tests unchanged.

### 5.4 Corrupt and failed terminations

Today a fetched message that does not decode is terminated with no metric and no log line
(only the optional `WithOnCorruptMessage` callback),
and a `Term()` that fails records neither a drop nor a counter.

- New optional collector interface `types.ReplayStreamMetrics`
  (shared with 5.3) with `IncReplayCorrupt(cluster ClusterID)`, `IncReplayTermFailed(cluster ClusterID)`
  and `AddReplayEvicted(n int)`,
  series `{prefix}_replay_corrupt_total{cluster}`, `{prefix}_replay_term_failed_total{cluster}`
  and `{prefix}_replay_evicted_total`.
  `cluster` is the consumer's cluster, which is known even when the payload is not decodable.
- The worker owns replay-stream telemetry, as it owns every other replay metric and the logger.
  Decoding stays in `NATSReplayer.Dequeue`, but `handleCorrupt` reports through an observer
  the worker installs on the replayer when it is built, next to the retained-delivery setting
  (cluster, stream sequence, decode error, `Term` error);
  a replayer with no observer keeps today's callback-only behaviour.
  The observer records `IncReplayCorrupt`, records `IncReplayTermFailed` when the `Term` failed,
  logs one `Error` line with the sequence, then the existing callback runs with the composed error.
  The observer touches only the worker's collector and logger, which outlive `Stop`, so it is never cleared;
  a shared replayer is not a supported layout, and the last worker built wins.
- `termMessage` records `IncReplayTermFailed` on failure.
  Under the bounded policy a termination that fails on the last permitted delivery is still a loss
  (the server will not deliver the message again), so the drop is recorded with its original reason;
  under the retained policy the message comes back and is settled again, so nothing else is recorded.

Verification: worker tests with a fake message whose `Term` fails under both policies
(bounded on the last delivery records the drop once; retained records only the counter and the message is redelivered);
a replayer test with an undecodable payload whose `Term` succeeds (counter, log, callback, not fetched again)
and one whose `Term` fails (both counters, log, composed callback error);
a test that building a worker installs the observer.

### 5.3 Eviction event

Today nothing reports a message the stream removed on its own (`MaxAge`, `DiscardOld` under a limit);
the worker reads `State.Msgs` and `State.Subjects` once per second and never the sequence bounds.

- Opt-in: `replay.WithEvictionWatch()` on the NATS worker starts one goroutine that polls the unfiltered
  stream state once per second and is the single owner of the accounting;
  `PendingByCluster` and its subject-filtered reads are not involved.
  The option's Godoc states the assumption it encodes:
  this process runs the only workers on the stream.
- The signal is best effort by construction and is documented as
  "messages the stream removed without an acknowledgement from this process":
  acknowledgements are asynchronous, so a removal the server applied just before a poll
  whose acknowledgement the worker counts just after it is reported once and offset by the next interval's carry,
  and another process's acknowledgements are removals this process did not make.
  The counter and the event are a signal to investigate, never an exact loss count.
- Accounting per poll, from two consecutive states `a` and `b`:
  published = `b.LastSeq - a.LastSeq`; removed = `a.Msgs + published - b.Msgs`;
  evicted = max(0, removed - settled - credit), where settled is the number of acknowledgements and terminations
  the worker performed since the previous poll (a counter, not a set) and credit is the previous interval's
  leftover settlements: the old credit covers an interval's removals first, the interval's own settlements
  cover the rest, and only the settlements left over carry on, `credit' = max(0, settled - max(0, removed - credit))`,
  so an unused credit expires after one interval and a lost acknowledgement cannot mask later removals for good.
  Delayed negative acknowledgements are not settlements.
  The accounting applies only while `b.LastSeq >= a.LastSeq` and the stream is the one seeded
  (`StreamInfo.Created` unchanged); a recreated stream or a lower `LastSeq` reseeds the baseline and reports nothing.
  A purge, whole or partial, is a removal the process did not acknowledge and is reported;
  the stream state does not distinguish it from an eviction, and the docs say so.
  The first poll only seeds.
- Every positive count is reported as `AddReplayEvicted(n)` (no cluster label: the stream state does not say which
  subject a removed message had) and as one `types.EventReplayEvicted` (`replay_evicted`) event with `Count`
  and `Cluster` unset, through the worker's emitter:
  `replay.Worker` implements `helix.EventEmitterSetter`, and `autoInjectEventEmitter` visits `ClientConfig.ReplayWorker`
  before `ReplayWorker.Start` runs, with the constructor's error path clearing it.
  `replay.Worker` also implements `EvictionWatchEnabled() bool`;
  `orderedClusterEventKinds` and the reachability switch classify the kind as unreachable
  unless the replay worker reports the watch enabled.

Verification: a unit test driving the accounting through fake stream states
(seed, publish only, settle only, eviction, settlement after the poll and its one-interval credit,
whole and partial purge reported, recreated stream and a lower `LastSeq` reseeding)
asserting the counter and the event;
an embedded-NATS test with a short `MaxAge` that sees one event with the right count,
and none while messages are only acknowledged;
reachability tests with the watch on and off;
a test that the emitter is installed before the worker starts.

### 5.5 Message id

Today `Enqueue` publishes with `js.Publish` and no headers,
so a publish that times out on the client after the server stored the message is counted as a drop
although it will be replayed, and a retry would store it twice.

- `Enqueue` publishes with `PublishMsg` and, for an idempotent payload, `Nats-Msg-Id` set to the hex SHA-256
  of a canonical identity: a schema tag, the target cluster, the timestamp, the priority,
  a presence bit and the value for each consistency field,
  a variant tag (statement or batch), and either the statement with its arguments
  or the batch type, the statement count, and each statement with its arguments in order;
  every field length-prefixed, arguments encoded by the existing argument encoder.
  The envelope version is not part of it, so a wire-format change keeps ids stable;
  a future semantic field is added to the identity schema with a new schema tag.
- A non-idempotent payload (a counter update, or a statement marked so by the caller) carries no id:
  two distinct such writes can legitimately share every identity field within one microsecond,
  and JetStream would keep only one.
  Its publish is not safe to retry after an ambiguous timeout, and the docs say so.
- The argument encoder writes map keys in sorted order, so the same arguments always encode to the same bytes;
  decoding does not depend on key order.
- Two idempotent writes with the same cluster, timestamp, statement, and arguments are the same write:
  a replay is idempotent under the client-side timestamp, so storing it once is correct.
- The stream keeps JetStream's default duplicate window (two minutes);
  `WithDuplicateWindow(d)` on the replayer sets it for callers
  whose retries can start later than that after the first attempt.
  The docs state that the window bounds the delay between the first publish and its retry, not the publish timeout.
- A publish the server reports as a duplicate is a success (the message is already stored);
  the replayer has no logger, so nothing is logged.
- `docs/replay-system.md` explains the id, the window, and that a caller may retry `Enqueue` after a timeout.

Verification: unit tests that the id is stable across encodes, across map key order, for nested maps and batches,
differs when the arguments, the consistency presence or value, or the variant differ,
does not change with the envelope version, and is absent for a non-idempotent payload
(two distinct non-idempotent writes with identical fields are both stored);
an embedded-NATS test that enqueues the same payload twice and finds one message,
and one with a custom window.

### 5.6 Close drain documentation and mirror drain timeout

Today `Close` drains the mirror queue synchronously with no bound
(8192 captures, five seconds each in publisher mode is minutes) and the docs do not say so;
`replay.WithOnDrop`, `replay.WithOnError`, `mirror.WithOnDrop` and `mirror.WithOnError`
do not carry the rule that the callback must not call `Close`.

- `mirror.WithDrainTimeout(d)`, a soft bound on `Engine.Stop`:
  when `d` elapses the workers stop taking captures from the queue,
  every capture still queued is dropped exactly once
  (the engine's `DropHandler`, its dropped statistic,
  `AddMirrorDrainDropped(n int)` on the new optional interface
  `types.MirrorShutdownMetrics`, series `{prefix}_mirror_drain_dropped_total`, and one `Warn` line with the count),
  and `Stop` then waits for the captures already executing and their callbacks.
  `d` is the cutoff for starting new executions, not a bound on `Stop` or on `CQLClient.Close`:
  both wait for every in-flight execution and for every synchronous drop and error callback,
  whose delays add up, so a blocking callback holds `Close` for as long as it blocks.
  The Godoc says so, and the queue-depth gauge reaches zero when the drain ends.
  Zero keeps today's unbounded drain.
  Captures enqueued at the deadline are dropped by the same path.
  No root option: `WithMirror` and `WithMirrorPublisher` already take `mirror.Option` values.
- `CQLClient.Close` Godoc and `docs/mirror.md` state the synchronous drain, its cost, and the timeout;
  `docs/replay-system.md` states the worker `Stop` wait.
  `Close` keeps its order (mirror engine, then mirror replay worker, then events, then sessions),
  which the soft bound preserves because no worker outlives `Stop`.
- The no-`Close`-from-callback sentence is added to the four option Godocs above and to the two guides.

Verification: engine tests with a gated executor and a short timeout
(queued captures dropped once with handler, statistic, and counter;
the in-flight capture completes; `Stop` returns once it has),
a blocking drop handler, an enqueue racing the deadline, and repeated or concurrent `Stop`.

### 5.7 Flapping and probe counters

Phase 4 left two signals as events or log lines only:
`write_flapping` has no metric counterpart (the event guide names it as the single exception),
and a breaker probe reservation's outcome is only a log line.
The roadmap table lists this item so the PR can name it.

- `types.WriteFlappingMetrics` with `IncWriteFlapping(cluster ClusterID)`,
  series `{prefix}_write_flapping_total{cluster}`, recorded at the transition that emits the event.
- `types.BreakerProbeMetrics` with `IncCircuitBreakerProbe(cluster ClusterID, outcome string)`,
  series `{prefix}_circuit_breaker_probe_total{cluster,outcome}`, outcomes `succeeded`, `failed`, `abandoned`,
  recorded in `CompleteFailoverProbe` only after the token is accepted;
  a stale token records nothing and an unknown outcome records `abandoned`, as it is handled.
- `docs/cluster-events.md` drops the exception; `contrib/metrics/vm` implements both.

Verification: policy tests for the flapping counter at the cap and for every probe outcome,
a stale token, an unknown outcome, and exactly one increment per completion;
the event guide's table has a counterpart for every kind.

## Decisions (2026-09-04)

1. The read-route gauge follows the strategy's preference only; request-level overrides do not move it.
2. Every route transition is decided, applied, and enqueued under the strategy's transition mutex;
   the gauge is written outside it by a single-owner loop that rereads the latest preference.
   `PrimaryOnlyRead` gains a transition mutex for its writers and keeps `Select` lock-free.
3. One FIFO buffer with reserved admission (per-operation kinds capped at 128 of 160 slots) rather than lanes or coalescing,
   so the documented enqueue-order contract holds and the item stays additive;
   outbox drops are forwarded only from the drainer after policy locks are released,
   retained while no emitter is installed.
4. The eviction watch is opt-in (`replay.WithEvictionWatch()`), owned by one goroutine polling unfiltered stream state,
   counts removals from `Msgs` and `LastSeq` deltas minus this process's settlements,
   with a credit that covers the next interval first and then expires,
   reseeds on a recreated stream or a lower `LastSeq`, reports purges as removals, and is documented as best effort.
5. The message id hashes a canonical, schema-tagged identity of the payload, not the envelope bytes;
   the argument encoder sorts map keys; a non-idempotent payload carries no id.
6. The mirror drain timeout is the cutoff for starting new executions (drop the queue once, wait for in-flight work
   and callbacks), defaults to zero, and is a `mirror.Option` only.
7. 5.7 is added to the roadmap table, so the PR can close it like the others.
