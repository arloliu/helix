# v1.5.0 — Slice Read with FallbackRead

## Goal

Add multi-row read methods on `helix.Query` that participate in the existing
`FallbackRead` pipeline. Today `FallbackRead` only fires on single-row reads
(`Scan` / `MapScan`); callers that read multiple rows from one partition fall
back to `Iter`, which has no not-found signal and therefore cannot trigger a
silent retry on the alternative cluster.

### Motivating caller

A representative caller scans a bounded composite-key partition (e.g.,
`(tenant_id, status, bucket_id)`) via `QueryIterContext` to materialize a
small list of related rows. When the chosen cluster has not yet replayed
writes for that partition, the iter returns empty and the caller sees a
missing list with no signal to retry on the alternative cluster. The same
shape recurs anywhere a single partition is fanned out into a slice of
domain objects: per-tenant metadata lookups, per-entity child collections,
per-bucket index reads.

## Non-goals (v1.5.0)

- Streaming fallback — the not-found signal exists only after a full drain.
  Streaming consumers continue to use `Iter`.
- Reconciliation / dual-read merge — this is purely "prefer primary, retry
  on alternative when primary is empty". Partial-replication recovery is out
  of scope.
- Pagination across the fallback boundary — the slice methods drain the
  entire result set on a single cluster. Large result sets continue to use
  `Iter` with caller-managed paging.
- Reflection-based typed slice scanning (`SliceScan(*[]MyRow)` with cql
  struct tags). Out of scope; can layer on top later without API change.

## Public API

### Four new `Query` methods

Add to the `Query` interface in `cql_session.go`, mirroring the existing
`Scan` / `MapScan` pair shape:

```go
// SliceMap drains the query into a slice of column-name → value maps.
//
// Semantics match Iter().SliceMap() except:
//   - Participates in FallbackRead. If the selected cluster returns zero
//     rows AND FallbackRead is enabled, Helix silently retries on the
//     alternative cluster. Empty result on the alternative is returned
//     as (nil, nil).
//   - Bounded by MaxRows / DefaultMaxRows. Exceeding the bound returns
//     (nil, ErrRowLimitExceeded).
//
// The full result set is materialized in memory. Use Iter for unbounded
// or large result sets.
SliceMap() ([]map[string]any, error)
SliceMapContext(ctx context.Context) ([]map[string]any, error)

// SliceScan drains the query and invokes scanFn once per row.
//
// scanFn receives a RowScanner positioned at the current row; the caller
// uses RowScanner.Scan(dest...) to copy column values via the gocql
// destination-driven unmarshalling path (custom UnmarshalCQL, blob
// coercion, etc. are preserved). Returning a non-nil error from scanFn
// aborts iteration and propagates the error. The RowScanner is valid
// only for the duration of the callback — call Scan(dest...) inside
// scanFn; do not retain or use the RowScanner after scanFn returns.
//
// If scanFn is nil, SliceScan returns an error before any cluster
// contact — neither the primary nor the alternative cluster is queried.
//
// scanFn is invoked sequentially during the drain. SliceScan does NOT
// participate in standard executeRead failover for selected-cluster
// errors at all: any error from the selected cluster is returned to the
// caller without re-running on the alternative cluster, regardless of
// whether scanFn has been invoked yet. The conservative all-error rule
// prevents post-callback silent corruption — re-running on the alt
// would invoke scanFn a second time on rows that already mutated the
// caller's accumulator from the failed primary, returning
// (rowCount, nil) with corrupted partial+full state and no error
// signal. The same rule covers pre-callback errors so the library
// guarantee is unconditional rather than requiring callers to reason
// about timing. See "SliceScan failover semantics" below for the full
// rationale. FallbackRead empty-retry continues to apply: a selected
// cluster that returns zero rows triggers an alt-cluster retry; the
// alt's rows are the only ones scanFn observes in that case.
//
// Bounded by MaxRows / DefaultMaxRows.
SliceScan(scanFn func(r RowScanner) error) (rowCount int, err error)
SliceScanContext(ctx context.Context, scanFn func(r RowScanner) error) (int, error)
```

### `MaxRows` — required v1.5.0 surface

Add a per-query bound and a client-level default. **Not deferred**: shipping
without a bound would make migration from `Iter` (streaming, safe) to
`SliceMap` (unbounded buffer) a memory-cliff for the most likely adopters.

```go
// On Query
MaxRows(n int) Query   // 0 clears the per-query override and uses Config.DefaultMaxRows

// On Config (via WithDefaultMaxRows option)
helix.WithDefaultMaxRows(10_000)   // 0 = unbounded (default for backward-compat)
```

Resolution precedence: per-query `MaxRows(n)` (n > 0) > `Config.DefaultMaxRows`
(> 0) > unbounded.

The bound applies to **each cluster's drain independently**. Exceeding the
bound on the primary returns `ErrRowLimitExceeded` to the caller without
firing fallback (the answer wasn't "empty"; it was "too big"). The
alternative cluster is not probed in this case.

`MaxRows` applies only to the four new slice methods. `Iter` remains the
documented escape hatch for unbounded scans.

### `ErrRowLimitExceeded` — public sentinel, root re-exported

Add to `types/types.go` and re-export from `client.go` (matching the
existing `ErrNotFound` / `IsNotFound` pattern):

```go
// types/types.go
var ErrRowLimitExceeded = errors.New("helix: row limit exceeded")
func IsRowLimitExceeded(err error) bool { return errors.Is(err, ErrRowLimitExceeded) }

// client.go
var ErrRowLimitExceeded = types.ErrRowLimitExceeded
func IsRowLimitExceeded(err error) bool { return types.IsRowLimitExceeded(err) }
```

Callers should be able to write `errors.Is(err, helix.ErrRowLimitExceeded)`
without importing the `types` package — symmetric with how `ErrNotFound` is
already exposed.

### Per-statement opt-in (no change)

`FallbackRead()` continues to opt in per-query; the existing context helper
(`helix.WithFallbackRead`) and `Config.DefaultFallbackRead` apply unchanged.

```go
rows, err := client.Query("SELECT id, category, created_at FROM ... WHERE ...", args...).
    FallbackRead().
    MaxRows(10_000).
    SliceMapContext(ctx)
```

### `SliceScanAs[T any]` — generic helper (no reflection)

A small generic helper layered on top of `SliceScanContext` that
eliminates the per-row append boilerplate without introducing a
struct-tag reflection layer. Lives in `slice_helpers.go` at the root
package.

```go
// SliceScanAs runs q.SliceScanContext and collects each decoded row
// into a []T. The decode callback receives a RowScanner positioned at
// the current row and a *T to populate.
//
// If decode is nil, SliceScanAs returns an error before any cluster
// contact — symmetric with SliceScan's nil-scanFn contract.
//
// All semantics of the underlying SliceScan apply: FallbackRead,
// MaxRows / DefaultMaxRows bounding, page-size clamping, no standard
// failover for SliceScan, PageState short-circuit. The returned slice
// is nil when the query yields zero rows (matches SliceScan's
// (rowCount=0, err=nil) shape).
//
// On err != nil, the returned slice is nil — partial accumulator
// state is NOT exposed to the caller. Callers who need partial
// state should use SliceScan directly and manage the accumulator
// themselves.
func SliceScanAs[T any](
    ctx context.Context,
    q Query,
    decode func(r RowScanner, dst *T) error,
) ([]T, error) {
    if decode == nil {
        return nil, errNilSliceScanAsDecode
    }
    var out []T
    _, err := q.SliceScanContext(ctx, func(r RowScanner) error {
        var v T
        if derr := decode(r, &v); derr != nil {
            return derr
        }
        out = append(out, v)
        return nil
    })
    if err != nil {
        return nil, err
    }
    return out, nil
}
```

Caller:

```go
type EntityMetadata struct {
    ID        string
    Category  string
    CreatedAt time.Time
}

rows, err := helix.SliceScanAs(ctx,
    client.Query("SELECT id, category, created_at FROM ...").
        FallbackRead().
        MaxRows(10_000),
    func(r helix.RowScanner, dst *EntityMetadata) error {
        return r.Scan(&dst.ID, &dst.Category, &dst.CreatedAt)
    },
)
```

Notes:

- Pure additive helper — does not change `Query`'s interface and
  doesn't require any other changes to the v1.5.0 surface.
- No reflection, no struct tags, no `reflect` import. Reflection-based
  scanning remains a deferred item (see "Open items"). The helper
  preserves gocql's destination-driven unmarshalling because the
  caller's `decode` function uses `RowScanner.Scan(dest...)` directly.
- Generic free function, not a method, because Go does not allow type
  parameters on interface methods.
- Decode-callback errors abort the drain and propagate (same shape as
  `SliceScan`'s scanFn-error path).
- **Nil callback contract** (per GPT v7 review): both `SliceScan*` and
  `SliceScanAs[T]` validate their callback before any cluster contact
  and return an error if nil. Use unexported sentinels
  (`errNilSliceScanFn`, `errNilSliceScanAsDecode`) — callers should not
  branch on them; they are programmer-error indicators, not part of the
  recoverable error surface. Tests assert via `require.Error` /
  `require.ErrorContains`, not `errors.Is`.
- **Error → nil slice** (per GPT v4 review). On any error
  (decode-callback error, `ErrRowLimitExceeded`, ctx error, primary
  cluster error), the helper returns `(nil, err)` — the partial
  accumulator is not exposed. This deliberately diverges from the
  underlying `SliceScan`'s "scanFn-mutated state is undefined on
  err != nil" contract: as a convenience helper, `SliceScanAs`
  shouldn't propagate that footgun to its most ergonomic API.
  Matches the standard Go convention (`json.Unmarshal`,
  `os.ReadFile`, etc. all return zero on err). Callers who genuinely
  need the partial accumulator should use `SliceScan` directly with
  their own state management — clean separation.
- Allocation strategy: appends to a nil slice; if a caller wants a
  pre-allocated backing array (e.g., when MaxRows is set and they want
  one allocation), they can roll their own variant — keeping
  `SliceScanAs` minimal avoids design churn.

A `SliceMapAs[T]`-style helper for `SliceMap` is not provided; callers
who want typed rows should use `SliceScanAs`. `SliceMap` remains the
escape hatch for "give me whatever the driver returned as a map".

### Five contract clarifications (load-bearing)

These were identified in design review and must hold in the implementation.

#### 1. `SliceScan` failover semantics — streaming, no standard failover, narrow `RowScanner`

This clarification went through two rounds of review. The current shape
resolves three connected issues that the earlier draft handled poorly.

**Issue A — paradox in earlier draft.** A previous draft tried to satisfy
both full pre-callback materialization (so `scanFn` saw a stable
single-cluster view) AND type-aware destination scanning (preserving
gocql's custom `UnmarshalCQL`, blob coercion, etc.). Those are mutually
incompatible under a `func(RowScanner) error` callback shape: destination
types are only knowable by invoking `scanFn`, but invoking `scanFn` during
drain breaks the materialize-first guarantee.

Resolution: drop the materialize-first guarantee; preserve type-aware
scanning. `scanFn` is invoked sequentially during drain.

**Issue B — silent corruption under standard failover.** With streaming
`scanFn`, if the selected cluster errors mid-drain after some `scanFn`
calls and `executeRead` standard-failovers to the alt, the alt's full
drain runs `scanFn` again. Caller's accumulator now holds
partial-primary + full-alt rows AND `err == nil`. Caller has no signal
that a retry occurred. **Silent data corruption.**

Resolution: **`SliceScan` does NOT participate in standard executeRead
failover.** If the selected cluster errors mid-drain, the error is
returned to the caller as-is. The caller can retry the whole call with a
fresh accumulator. This is a hard library guarantee, not a caller
obligation.

`SliceMap` is unaffected — it buffers driver-side and the caller's return
value is committed only after a successful single-cluster drain.

> **Why no `resetFn` parameter (Gemini v2 suggestion):** A
> `SliceScan(scanFn, resetFn)` shape was considered and rejected. Reasons:
> (a) clutters the API for the common case; (b) doesn't generalize to
> scanFn implementations that emit to channels, write to a DB, or push
> through other sinks where "reset" has no clean meaning; (c) easy to
> forget to wire and silently broken when omitted; (d) the library still
> needs the same internal "no failover after first callback" decision to
> know when to fire `resetFn`, so the no-failover rule is a strict
> simplification of the resetFn design with the same safety guarantee.

> **Why not document "scanFn must be idempotent" (Gemini v2 alternate):**
> Considered and rejected. Most callers will append-to-slice, which is
> not idempotent under retry. A documentation-only contract would silently
> break the common case. Loud failure beats silent corruption.

> **FallbackRead empty-retry remains safe:** when the selected cluster
> returns zero rows, scanFn was never invoked on that cluster. The alt's
> rows are the only ones scanFn observes. Single-cluster atomic view holds
> for this case.

**Issue C — `RowScanner` vs `Scanner`.** The existing `Scanner` interface
(`cql_session.go:522-532`) exposes `Next() bool`, `Scan(dest...) error`,
and `Err() error`. Inside `scanFn`, only `Scan` is meaningful — the
engine advances the underlying iter between callbacks. Passing the full
`Scanner` would expose `Next` and `Err` as no-ops or footguns.

Resolution: introduce a narrower `RowScanner` interface in
`cql_session.go`:

```go
// RowScanner is the per-row scanner passed to SliceScan's callback.
// Inside the callback, call Scan(dest...) to bind the current row's
// columns into the caller's destination pointers via the same
// destination-driven unmarshalling path used by Iter.Scanner().Scan.
//
// RowScanner is valid only for the duration of the callback. Callers
// MUST call Scan(dest...) inside scanFn and MUST NOT retain or use
// the RowScanner after scanFn returns — by the next callback, the
// underlying scanner has advanced to a new row, and after the drain
// the scanner is invalidated by Scanner.Err() (sets is.iter = nil,
// is.cols = nil, is.valid = false). A retained RowScanner.Scan call
// fails loudly (nil deref or "iterator already closed"), not silently
// — but the contract still rules out the misuse. Per GPT v14 LOW.
type RowScanner interface {
    Scan(dest ...any) error
}
```

The full `Scanner` interface stays unchanged for direct iterator users.

#### 2. Drain-aware fallback for slice methods

`executeFallbackRead` (`cql_client.go:2079-2080`) intentionally bypasses
drain state on the alternative cluster — a draining cluster may still hold
the data the user is asking about. For single-row `Scan` this is binary
(have it / don't). **For multi-row reads, a draining alternative can return
partial state**: caller gets "17 rows" when ground truth is "23 rows, alt is
mid-drain".

Decision: when the slice methods would invoke `executeFallbackRead`, **skip
the alternative if it is draining** and return the primary's empty result
directly. This is opt-out-able later via an explicit per-query flag if a
caller demonstrates a need; v1.5.0 ships with the safer default.

Implementation surface:

- `executeFallbackRead` gains a `skipDrainingAlt bool` parameter (or
  equivalent through a new variant). Single-row callers (`Scan` / `MapScan`)
  pass `false` — behavior unchanged. Slice callers pass `true`.
- The drain check uses the same `getDrainStates` / `clusterIsDraining`
  helpers `executeRead` already uses.

#### 3. `MaxRows` behavior at boundaries

- `MaxRows(0)` on `Query` means "use `DefaultMaxRows`"; `WithDefaultMaxRows(0)`
  means "no bound" (current behavior). Negative values to `MaxRows` panic at
  call time (programmer error, same as gocql's `PageSize(-1)` convention).
- **Off-by-one spec**: `MaxRows(N)` admits up to N rows; the read aborts
  upon detecting an (N+1)th row from the underlying iter. Return shape
  on overflow:
  - `SliceMap` → `(nil, ErrRowLimitExceeded)`. The map slice is
    materialized internally during drain; on overflow it is discarded
    and never exposed to the caller.
  - `SliceScan` → `(N, ErrRowLimitExceeded)` where N is the number of
    `scanFn` invocations that returned `nil` (i.e., **successful**
    callbacks completed) before the overflow trigger. **rowCount is
    the successful callback count — invocations that returned an error
    do NOT contribute.** The caller's accumulator has been mutated by
    those N successful callbacks and is undefined per the SliceScan
    contract — but rowCount accurately reports "your callback
    successfully appended N rows, then we aborted before invoking it
    again". Returning `0` on overflow would lie about what the
    caller's accumulator looks like.

    Note on the failing-callback edge case: if `scanFn` is invoked,
    partially mutates caller state, then returns an error, that
    partial mutation is part of the already-documented undefined
    accumulator state on `err != nil`. It is NOT counted in
    `rowCount` — only callbacks that returned nil are.

- **`SliceScan` rowCount semantics on ANY error** (per GPT v5 review):
  rowCount = number of `scanFn` invocations that completed successfully
  before the error. Holds for:
  - `MaxRows` overflow (rowCount = N where N is the bound)
  - `scanFn` returning an error (rowCount = invocations before that
    return)
  - Primary mid-drain real error (rowCount = invocations before the
    underlying iter errored)
  - `ctx.Canceled` / `DeadlineExceeded` from primary (rowCount =
    invocations before cancellation observed)

  When `err != nil`, the rowCount is diagnostic-only — the accumulator
  state is undefined per the SliceScan failover contract (clarification
  #1). Callers should reset their accumulator on `err != nil`
  regardless of rowCount.
- **Enforcement mechanism — two distinct counted-drain helpers**:
  - `SliceMap` uses `for iter.MapScan(m) { ... }` in a counted loop.
  - `SliceScan` uses `scanner := iter.Scanner(); for scanner.Next() {
    scanFn(rowScannerAdapter{scanner}) }` then `scanner.Err()`.

  Do NOT use `iter.SliceMap()` (the bulk-drain adapter method) for the
  underlying drain in either Helix method — it materializes the full
  result before any size check, which defeats the bound entirely.

- **Page-size clamp (load-bearing for memory safety)**: a counted Helix
  loop only bounds Helix's own materialization (`[]map[string]any` for
  SliceMap, scanFn invocations for SliceScan). It does NOT bound the
  underlying driver's per-page fetch — when `PageSize` is large, the
  driver allocates and receives the full page from the network before
  Helix can stop. To make `MaxRows` an actual memory bound, slice methods
  clamp the underlying query page size to `min(userPageSize,
  effectiveMaxRows+1)` whenever `effectiveMaxRows > 0`. If the user did
  not set `PageSize`, the slice method sets it to `effectiveMaxRows+1`.
  The `+1` lets Helix detect overflow (drain reaches row N+1) without
  fetching a second page.

  This means `MaxRows` provides two distinct guarantees:
  1. Helix's accumulator is bounded by N+1 rows.
  2. The driver's per-page buffer is bounded by N+1 rows.

  Without the clamp, only guarantee 1 holds, and the original
  memory-safety claim was overstated. Document both explicitly.
- The bound applies independently per cluster. If the primary fails to drain
  (real error → standard failover) and the alternative also has > N rows,
  the alternative read returns `ErrRowLimitExceeded` exactly like the
  primary would have.
- `ErrRowLimitExceeded` MUST be recognized as a third terminal sentinel
  (alongside `nil` and `ErrNotFound`) at every read-pipeline site that
  currently special-cases `ErrNotFound`. Per GPT v2 review verification
  against the codebase, this includes:
  - **Single-cluster fast path** (`cql_client.go:1864`): currently
    `!types.IsNotFound(err)` gates `IncReadError`. Must extend.
  - **`executeRead` primary path** (`cql_client.go:1906`): the
    not-found short-circuit. Must add a row-limit short-circuit that
    bypasses the failure path entirely (no failover, no metrics, no
    `RecordFailure`).
  - **`tryFallbackCluster`** (`cql_client.go:2028-2042`): currently
    suppresses `ErrNotFound`; must also suppress (= propagate as-is)
    `ErrRowLimitExceeded` rather than wrapping it in `DualClusterError`
    or recording health failure.
  - **`executeFallbackRead`** (`cql_client.go:2099-2123`): the
    alt-error suppression rule. Must propagate `ErrRowLimitExceeded`
    instead of swallowing.
  - **`recordOpOutcomeAt`** (`cql_client.go:432-452`): the operational
    sentinel exclusion list (`ErrNotFound`, `ErrWriteAsync`,
    `ErrWriteDropped`, `ErrClusterDegraded`, `ErrClusterDraining`).
    `ErrRowLimitExceeded` must be added so an accidental call path
    can't poison auto-refresh.
  Recommended implementation: introduce `isReadTerminalNonHealth(err)`
  in `cql_client.go` covering both `ErrNotFound` and `ErrRowLimitExceeded`,
  and use it consistently at every site above. Cleaner than threading
  individual `errors.Is` checks and prevents future drift if a fourth
  sentinel is added.

#### 4. Alt-error during FallbackRead must not silently expose partial state

This clarification addresses GPT v10's HIGH finding (and an analogous
hazard for `SliceMap` surfaced in self-review). The pre-v10 plan
suppressed all non-context, non-row-limit alt errors to `ErrNotFound`
under the "availability beats failure" rule — a rule borrowed from
`Scan`'s single-row binary semantics. For multi-row drains, that rule
silently exposes partial state in two distinct ways:

**Shape A — `SliceScan` (caller-visible mutation via `scanFn`).**

1. Primary returns 0 rows → `executeFallbackRead` invoked.
2. Alt's drain invokes `scanFn` N times, mutating the caller's accumulator.
3. Alt errors mid-drain (e.g., generic gocql network error).
4. Old rule: suppress alt error to `ErrNotFound` → public method
   returns `(rowCount=N, err=nil)`. Caller sees a "successful read of N
   rows" but their accumulator has the *partial* alt drain — the actual
   partition may have had many more rows. **Silent partial success.**

**Resolution:** `propagateAltErr` is implemented as a **closure that
captures a `scanFnInvokedOnAlt bool` flag** (NOT `rowCount`; see
"Why not `rowCount > 0`" below). For `SliceScan`, the predicate
returns `true` (propagate) when:

- `errors.Is(err, types.ErrRowLimitExceeded)` — application cap; OR
- `errors.Is(err, context.Canceled)` — caller-driven termination; OR
- `errors.Is(err, context.DeadlineExceeded)` — caller-driven termination; OR
- **`scanFnInvokedOnAlt`** — `scanFn` was invoked at least once on the alt drain
  (whether it returned successfully or with an error).

The `scanFnInvokedOnAlt` clause is load-bearing: any alt error — iter
error, ctx error, OR a `scanFn`-returned error — that occurred *after
or during* a callback invocation propagates. If alt errored before
invoking `scanFn` even once (e.g., immediate connection failure on alt
before any row was admitted), the predicate returns `false` and
suppression preserves today's availability behavior — no corruption
risk because no caller mutation occurred.

**Why not `rowCount > 0`** (per GPT v11 review). The v10 → v11 round
used `rowCount > 0` as the proxy. That was wrong: `rowCount` is
defined as **successful callbacks only** (clarification #3), so a
`scanFn` that is invoked on alt's first row, partially mutates
caller state, and returns an error leaves `rowCount = 0` — the
predicate would suppress the error to `ErrNotFound` and the public
method would return `(0, nil)`, silently swallowing the
caller-returned `scanFn` error. That violates the public API
contract ("Returning a non-nil error from scanFn aborts iteration
and propagates the error" — Public API §) and exposes the same
silent-partial-success class the v10 fix was meant to close, just
on a narrower path. Tracking `scanFnInvokedOnAlt` separately fixes
both issues without changing the meaning of `rowCount` or
regressing the alt-error-before-any-callback availability case.

**Implementation note: the wrapped-scanFn pattern.** The flag is set
by wrapping the user's `scanFn` at the public-method layer rather
than threading a pointer through the helper. This keeps
`drainIterScanWithLimit`'s signature stable and co-locates the flag
with the closure that needs to read it:

```go
var rowCount int
var scanFnInvokedOnAlt bool
readFunc := func(ctx context.Context, sess cql.Session) error {
    query := sess.Query(q.statement, q.values...)
    query = q.applyConfig(query) // includes PageState + page-size clamp
    iter := query.IterContext(ctx) // ctx-aware: per GPT v14 HIGH (v15) — see "ctx-aware iterator binding" below
    wrapped := func(r RowScanner) error {
        scanFnInvokedOnAlt = true  // set BEFORE calling user scanFn
        return scanFn(r)            // user's error/success comes back to drain helper
    }
    n, err := drainIterScanWithLimit(iter, max, wrapped)
    rowCount = n
    return err
}
```

Same readFunc is invoked twice (primary first, alt second) by
executeFallbackRead. Primary's empty drain never enters the loop,
so `scanFnInvokedOnAlt` stays false through primary's run. Alt's
drain may set it to true before any error is observed. The flag's
name is intentionally "OnAlt" because the only path that reads it
is the FallbackRead alt-error suppression rule — primary errors are
never routed through `propagateAltErr` (SliceScan does not
standard-failover; primary errors return directly).

Sequencing: `executeFallbackRead` invokes alt's `readFunc` synchronously
and only evaluates `propagateAltErr` after `readFunc` returns. The
closure variable is therefore consistent — no atomic needed.

**Shape B — `SliceMap` (driver-buffered, but partial accumulator could
leak through closure capture).**

`SliceMap`'s `readFunc` closure captures `rows []map[string]any` from
`drainIterToSliceMapWithLimit`. When alt errors mid-drain, the helper
returns `(partialRows, err)`. If the public method then naively returns
`(closureCapturedRows, translateErr(err))`, suppression-to-`ErrNotFound`
becomes `(partialRows, nil)` — same silent partial success.

**Resolution:** the `SliceMap` public method MUST discard the captured
rows on **any** non-nil error from the read pipeline, including the
suppressed-to-`ErrNotFound` case. Two acceptable implementations:

1. **Helper-level:** `drainIterToSliceMapWithLimit` returns `(nil, err)`
   on any error path (not only `ErrRowLimitExceeded`). The mid-drain
   close-error and `MapScan`-error paths zero out `rows` before
   returning. Update the helper's return contract Godoc accordingly.
2. **Public-method-level:** the public `SliceMapContext` only commits
   the closure-captured rows when the pipeline returns `nil`. On any
   error (including `ErrNotFound` translated to `(nil, nil)`), the
   captured rows are NOT returned to the caller.

Either is fine; the implementation MUST pick one and lock it with a
test (`TestSliceMap_AltErroredMidDrain_NoPartialRowsExposed`). The
plan recommends option 1 for symmetry with the
`(nil, ErrRowLimitExceeded)` return shape that the helper already uses
for overflow.

**Why suppress at all?** For SliceScan-before-callback and SliceMap
post-discard, suppression preserves the original FallbackRead
availability promise: when both clusters are effectively unable to
serve the read (primary empty + alt unhealthy/transient), the caller
gets `(nil, nil)` / `(0, nil)` rather than an error they cannot
distinguish from a real cluster failure. `IncReadError` + `RecordFailure`
on the alt continues to fire so the unhealthy alt is still observable
operationally.

**Observability:** `IncReadError` and `RecordFailure` are recorded on
the alt cluster for **real cluster errors** (gocql iter errors,
network errors, scanFn-returned errors) regardless of whether the
error is propagated or suppressed. The propagation decision (governed
by `propagateAltErr`) affects only the caller-visible return value.
**Health classification is governed separately by `nonHealthAltErr`
plus the existing `isReadTerminalNonHealth` data-sentinel check** —
see clarification #5 below for the split rationale and which errors
skip health recording.

#### 5. Propagation and health classification are independent

This clarification addresses GPT v12's finding #1 — the v12 plan was
contradictory. The semantics table promised "no health impact" for
slice fallback alt ctx errors; phase 5 said health is recorded
"regardless of propagation". Both cannot be right. Resolution:

- **Caller-visible propagation** is governed by `propagateAltErr`. For
  any non-`ErrNotFound` alt error, the predicate returns `true` to
  propagate as-is or `false` to suppress to `ErrNotFound`.
- **Health classification** is governed by **two layered checks** at
  the executeFallbackRead alt-error path:
  1. `isReadTerminalNonHealth(err)` (the existing data-sentinel
     check covering `ErrNotFound` and `ErrRowLimitExceeded`).
     Slice methods inherit this directly — no slice-specific
     plumbing needed for these.
  2. `nonHealthAltErr(err)` (NEW per GPT v12). A
     `fallbackReadOptions` predicate that lets slice call sites
     classify additional errors as caller-driven / non-cluster-fault.
     For v1.5.0, slice methods use this for `context.Canceled` and
     `context.DeadlineExceeded`.
- If either check returns true, `executeFallbackRead` skips
  `IncReadError`, `recordOpOutcome`, AND `RecordFailure` on the alt
  cluster. Otherwise health is recorded as usual.

**Why split into two predicates instead of one unified
`nonHealthAltErr` covering all four sentinels (ErrNotFound +
ErrRowLimitExceeded + ctx pair)?** Cross-reviewer note for Gemini /
GPT v13: GPT v12's recommendation suggested including
`ErrRowLimitExceeded` in `nonHealthAltErr`. **Disagreed.** Reasons:

- `isReadTerminalNonHealth(err)` is already required at FIVE
  pipeline sites per phase 1 (single-cluster fast path,
  executeRead primary error branch, tryFallbackCluster,
  executeFallbackRead alt-error path, recordOpOutcomeAt exclusion
  list). It exists as a global "data-sentinel = no health impact"
  rule, independent of slice methods.
- Folding `ErrRowLimitExceeded` into `nonHealthAltErr` would make
  the rule slice-specific at one site (executeFallbackRead), which
  is misleading — the rule must hold at all five sites regardless
  of caller method. Two callers needing to register the same
  predicate is a bug-magnet.
- The conceptual distinction is real and worth preserving: data
  sentinels (`ErrNotFound`, `ErrRowLimitExceeded`) are
  application-level semantics — the cluster behaved correctly, the
  outcome simply isn't "got data". Caller-driven errors (ctx pair)
  are a different class — the cluster might have been about to
  succeed, but the caller withdrew. Mixing them blurs the
  abstraction and makes future additions harder to reason about.
- v1.5.0 ships with both predicates; if a future round wants to
  collapse them, that's a refactor with its own design choice — not
  something to do reactively under a single review's pushback.

The split is consistent with how the propagation rules layer:
`propagateAltErr` for slice-specific propagation, `isReadTerminalNonHealth`
applied uniformly across the pipeline. Health classification mirrors
that structure.

**What about scanFn-returned errors and SliceScan iter errors?** Those
continue to record health (same as today's "real alt error" rule):

- iter errors from gocql mid-drain are real cluster faults — record
  as such.
- scanFn-returned errors are application-level (caller's decoder
  bug), but distinguishing them from iter errors at the
  executeFallbackRead boundary requires extra plumbing
  (`scanFnErrorOnAlt` flag tracking the most-recently-returned
  callback error, separate from `scanFnInvokedOnAlt`, with the
  predicate matching via `errors.Is`). v1.5.0 does NOT distinguish
  — both record health on alt. Rationale: the plumbing cost is
  real (a second closure-captured value, careful sequencing across
  primary/alt readFunc reuse, additional test coverage) and the
  ambiguity it resolves is an edge case (caller has a buggy
  decoder AND uses FallbackRead AND the alt path is hit AND the
  decoder happens to fail there before any iter error surfaces).
  Worse, in the rare case where a buggy decoder coincides with a
  genuine cluster issue, falsely attributing the cluster signal
  to the decoder would actively HARM observability — better to
  conservatively record health and let operators investigate. A
  future round can add the distinction if a caller surfaces a
  real-world need.

## Documented caveats (no design change required)

- **Latency doubling on legitimately-empty queries.** With
  `DefaultFallbackRead=true`, `SliceMap*` / `SliceScan*` calls against a
  legitimately-empty result cost a round-trip to the alternative cluster —
  **except calls with `PageState` set**, which bypass FallbackRead empty-retry
  entirely (see PageState caveat below) because cursor tokens are
  cluster-local. For queries whose natural answer is often empty (sparse
  indexes, cold partitions), leave `FallbackRead` off. Migration risk for
  fleets that already enabled the default — call this out in the upgrade note.
- **`SliceScan` does NOT auto-failover on real cluster errors.** Unlike
  `Scan` and `SliceMap`, `SliceScan` propagates the primary cluster's
  error directly without re-running on the alternative. This is
  deliberate: re-running would invoke `scanFn` a second time on the alt's
  rows after the caller's accumulator already received partial state from
  the failed primary, and the final result `(rowCount, nil)` would
  contain partial+full rows with no error signal. Callers that need
  cross-cluster retry on real errors should use `SliceMap` and walk the
  returned `[]map[string]any`, OR catch the error and retry the
  `SliceScan` call themselves with a fresh accumulator. The
  `FallbackRead` empty-retry path is unaffected — it remains active for
  `SliceScan`.
- **`SliceMap` standard failover doubles the latency/memory budget.**
  When the selected cluster fails mid-drain with a real error for a
  `SliceMap` call, `tryFallbackCluster` re-runs the full readFunc on the
  alt → another full drain. Two near-complete materializations against
  the same deadline. Document and recommend tightening `MaxRows` for
  callers operating near memory limits. (`SliceScan` doesn't have this
  issue because it doesn't standard-failover at all — see above.)
- **Partial reads from a draining primary.** `executeRead`'s drain-aware
  selection already steers away from a draining cluster when the alternative
  is healthy. But when (a) both clusters are draining, or (b) an
  `AllowedClusters` override silently fell over to a non-draining alternate
  via override-resolution drain-filtering, the selected primary can return
  partial state. (Note: `resolveReadTarget` DOES drain-filter override
  entries by default — `cql_client.go:1280-1297` — and falls back to the
  next entry, so the override does not "bypass drain" except when ALL
  override entries are draining, in which case the resolver returns
  `ErrNoValidClusters`.) `Scan` is unaffected; slice methods inherit the
  partial-read risk on the override-fallback path. Callers needing strict
  consistency during drain should use `PrimaryOnlyRead` or operationally
  exclude the draining cluster.
- **`PageState` disables ALL cross-cluster retry on slice methods.** When
  `q.pageState != nil`, slice methods bypass both `FallbackRead`
  empty-retry AND any standard `executeRead` failover. This is broader
  than just FallbackRead because `PageState` cursors are opaque
  per-cluster — sending one to the alternative cluster is unsound
  regardless of what triggered the retry. Document in the Godoc and the
  user guide; do not rely on observing the precedence at runtime.
- **`PageState` cluster-origin affinity is the caller's responsibility.**
  Disabling cross-cluster retry prevents Helix from sending an
  alt-cluster's cursor to the wrong cluster *during a single slice call*.
  It does NOT guarantee the *initial* selected cluster matches the
  cluster that produced the cursor — read-strategy variability
  (e.g., `RoundRobinRead` rotating selection between page calls) and
  `AllowedClusters` membership changes (the function returning a
  different ordered set on the next call) can still steer the next
  paged call to a different cluster than the previous page came from.
  These remain caller-managed risks; v1.5.0 does not auto-pin cursor
  affinity. Two specific cursor-leak vectors that v1.5.0 DOES plug for
  the new slice + PageState path:
    1. **Drain-aware initial rerouting** — fixed by
       `preserveSelectedCluster=true`, which suppresses the executeRead
       drain-swap step for paged slice calls (clarification #3 / phase 4).
    2. **`AllowedClusters` override drain-filtering** (per GPT v9
       review) — when `preserveSelectedCluster=true`,
       `resolveReadTarget` returns the first known override entry as-is
       and fails closed with `types.ErrNoValidClusters` if it is
       draining, instead of silently falling over to the second entry
       and shipping the cursor to the wrong cluster (phase 1 / phase 4).
  Callers using `PageState` across pages should still pin cluster
  affinity via a STABLE `AllowedClusters` set, a stable read strategy,
  or application-side cluster tagging. A future `(ClusterID, PageState)`
  pair API is tracked in deferred items.

  **Scope note (intentional asymmetry).** v1.5.0 plugs (1) and (2) only
  for the four new slice methods — i.e., when the caller routes through
  `SliceMap*` / `SliceScan*` with `q.pageState != nil`. Pre-existing
  `Iter` + `PageState` + `AllowedClusters` callers continue to manage
  cluster affinity themselves; their behavior is unchanged in v1.5.0.
  Reason: changing `Iter` semantics is out of scope (no API addition can
  signal "I'm using PageState across pages, please preserve affinity"
  without a behavioral break). The deferred `(ClusterID, PageState)`
  pair API is the planned long-term fix; until then the asymmetry is
  documented, not silently inconsistent.
- **DX inconsistency.** `Scan` returns `ErrNotFound` on empty; the slice
  methods return `(nil, nil)` / `(0, nil)`. Deliberate (matches
  `Iter().SliceMap()`), but error-prone. Documentation must call out: do not
  use `errors.Is(err, ErrNotFound)` with the slice methods — check
  `len(rows) == 0` (or `rowCount == 0`) instead.
- **Partial-replication blind spot.** Primary returns N > 0 rows where some
  are missing under partial replication: slice methods return what the
  primary had. Same caveat as today's `Iter`. If under-replication matters,
  callers need a different mechanism.
- **`IncReadDivergence` semantics weaker for slice.** The metric fires when
  primary-empty and alt-non-empty. For slice queries this conflates real
  divergence with under-replication where the alt happens to have something.
  One-line note in metric docs; no metric change in v1.5.0.
- **Replay-lag amplification.** During cluster-wide replay backlog, every
  slice read with `FallbackRead` doubles QPS on the lagged cluster while
  it's already behind. Worse than for `Scan` because slice queries are
  typically heavier. Mention in the runbook section.

## Implementation phases

This plan was developed across multiple review rounds (Gemini + GPT) on
Opus 4.7 (1M ctx). The risk-bearing invariants are subtle and span layers:
`RecordFailure` called exactly once across two read-helper layers, three
terminal sentinels at five pipeline sites, **four** distinct
PageState-leak vectors (failover / empty-retry / drain-aware re-selection
/ `AllowedClusters` override drain-filter), and the asymmetric "no
standard failover for SliceScan but full executeRead for SliceMap" rule.
A model that drops one of these silently produces code that passes tests
and leaks in production.

     themselves. The clean shape:

     ```go
     // primaryAttemptResult: structured outcome of one primary read
     // attempt. Holds enough state for either failover or no-failover
     // callers to record terminal signals correctly.
     //
     // attempted=false means no read was sent to any cluster (client
     // closed, resolveReadTarget failed, etc.) — wrappers MUST NOT
     // emit cluster metrics or call cluster-health functions in that
     // case. err carries the pre-attempt error.
     //
     // attempted=true means a read was sent and metrics were recorded
     // (IncReadTotal, ObserveReadDuration). err is nil on success or
     // the cluster's error.
     type primaryAttemptResult struct {
         attempted bool
         target    readTarget    // valid only when attempted=true OR resolveReadTarget succeeded
         selected  ClusterID     // valid only when attempted=true
         elapsed   float64       // valid only when attempted=true
         err       error
     }

     // runPrimaryRead: low-level shared helper. Handles client-closed
     // check, resolveReadTarget(ctx, opts) (signature extended in v10
     // to thread opts.preserveSelectedCluster down to override
     // resolution — see "resolveReadTarget signature change" below),
     // single-cluster fast path, and dual-cluster primary-attempt
     // selection (honoring opts.preserveSelectedCluster to skip
     // drain-aware re-selection).
     // Records ONLY metrics (IncReadTotal, ObserveReadDuration) and
     // ONLY when attempted=true. Does NOT call IncReadError,
     // recordReadSuccess, recordOpOutcome, or RecordFailure — those
     // are caller-owned based on whether the caller intends to failover.
     func (c *CQLClient) runPrimaryRead(
         ctx context.Context, opts readOptions,
         readFunc func(context.Context, cql.Session) error,
     ) primaryAttemptResult

     // executeReadNoFailover: wraps runPrimaryRead. On real error,
     // records ALL terminal signals (IncReadError, recordOpOutcome,
     // RecordFailure) and returns without failing over. May invoke
     // executeFallbackRead on empty-result if opts.fallbackRead.
     // Used by SliceScan always; SliceMap when q.pageState != nil.
     func (c *CQLClient) executeReadNoFailover(
         ctx context.Context, opts readOptions,
         readFunc func(context.Context, cql.Session) error,
     ) error

     // executeRead: wraps runPrimaryRead. On real error, records
     // IncReadError + recordOpOutcome (NOT RecordFailure — failover
     // paths own that), then enters one failover path. Behavioral
     // parity with today's executeRead. Used by Scan, MapScan, and
     // SliceMap when q.pageState == nil.
     func (c *CQLClient) executeRead(
         ctx context.Context, opts readOptions,
         readFunc func(context.Context, cql.Session) error,
     ) error
     ```

     Single ownership rule: **`RecordFailure` is called exactly once per
     primary failure**, by whichever layer "owns" the no-failover
     decision (the no-failover wrapper, OR the failover branch in
     `executeRead`). Never both. This is the load-bearing invariant
     from GPT v4's review.

     **Wrapper ownership boundaries** (per GPT v5 review):
     - `attempted=false` (pre-attempt error: client closed,
       `resolveReadTarget` failed, etc.) → wrappers return
       `result.err` as-is. NO cluster metrics, NO cluster-health
       calls, NO sentinel recognition (pre-attempt errors are not
       sentinels). Both wrappers behave identically here.
     - `attempted=true && err == nil` (success) → wrappers call
       `recordReadSuccess(selected, elapsed, snap.active)` and
       `recordOpOutcome(selected, nil)`. Both wrappers behave
       identically here.
     - `attempted=true && isReadTerminalNonHealth(err)` (`ErrNotFound`
       or `ErrRowLimitExceeded`) → wrappers do NOT call IncReadError,
       recordOpOutcome, or RecordFailure. For `ErrNotFound` with
       `opts.fallbackRead` AND `!c.IsSingleCluster()`, wrappers invoke
       `executeFallbackRead` (this is an empty-retry, not failover).
       **In single-cluster mode, the wrappers return `ErrNotFound`
       as-is without invoking `executeFallbackRead`** — there is no
       second cluster to retry against, and `getSession(ClusterB)`
       returns session A in single-cluster mode. Calling
       `executeFallbackRead` blindly would issue a second read against
       session A while accounting it as cluster B metrics/health,
       violating today's `TestFallback_SingleCluster_FallbackRead_ReturnsNotFound`
       contract for `Scan` and the analogous slice-method contracts.
       Public methods translate the resulting `ErrNotFound` to
       `(nil, nil)` / `(0, nil)` for slice methods. (Per GPT v10
       review.) For `ErrRowLimitExceeded`, both wrappers return as-is
       regardless of single/dual-cluster mode.
     - `attempted=true && err is real error` → diverges:
       - `executeReadNoFailover`: records IncReadError +
         recordOpOutcome + RecordFailure, returns the error.
       - `executeRead`: records IncReadError + recordOpOutcome (NOT
         RecordFailure), then enters one failover branch (the
         failover branch records RecordFailure exactly once).

   - **`resolveReadTarget` signature change (per GPT v9 review)** —
     extend from `resolveReadTarget(ctx) readTarget` to
     `resolveReadTarget(ctx, opts readOptions) readTarget`. Three
     existing call sites updated (`cql_client.go:1846`, `:2333`,
     `:2582`); they pass the `readOptions` they already have, so
     non-PageState callers are bit-for-bit equivalent (zero-value
     `preserveSelectedCluster=false` preserves today's drain-filter
     behavior).

     New behavior gated by `opts.preserveSelectedCluster=true` (set by
     slice methods when `q.pageState != nil`):
     - **Skip override drain-filter.** Today's loop at
       `cql_client.go:1280-1297` does
       `if c.clusterIsDraining(entry, ...) { continue }` for every
       known override entry. With `preserveSelectedCluster=true`, the
       loop instead returns the FIRST known entry as-is.
     - **Fail closed if first entry is draining.** If that first known
       entry is currently draining, return
       `readTarget{err: types.ErrNoValidClusters}` (reuse the existing
       sentinel from line 1309 — same operational meaning: caller's
       chosen cluster set is unusable due to drain). Do NOT silently
       fall over to the second entry, because that would ship the
       opaque cursor to the wrong cluster.
     - **Single-cluster mode is unchanged** — existing guard at
       `cql_client.go:1258-1276` is independent of drain state.
     - **Empty / nil-fn paths unchanged** — they go through
       `normalSelect`, which is independent of override drain-filter.

   - Tests: focused tests in `cql_client_test.go` confirming the three
     guarantees (no health impact, no failover, no metric inc) at each
     of the five sentinel sites. Plus:
     - `executeReadNoFailover` emits the same metrics, health calls,

     - `RecordFailure` is called **exactly once** for a normal-failover

     - `RecordFailure` is called **exactly once** for a no-failover

     (`Scan(dest ...any) error` only).
   - `cqlQuery.SliceMap` / `SliceMapContext`: counted-drain helper
     `drainIterToSliceMapWithLimit` using `for iter.MapScan(m)` in a
     bounded loop, then `iter.Close()`. **Goes through `executeRead`**
     by default so standard failover applies (driver-side buffering
     means transparent retry is safe); switches to `executeReadNoFailover`
     when `q.pageState != nil` per the mechanical option-derivation rule
     below.
   - `cqlQuery.SliceScan` / `SliceScanContext`: counted-drain helper
     `drainIterScanWithLimit` using
     `scanner := iter.Scanner(); for scanner.Next() { scanFn(rowScannerAdapter{scanner}) }`
     then `scanner.Err()`. **Goes through `executeReadNoFailover`** (from

     bookkeeping but never enters standard failover. Only invokes

     scanFn was not invoked on the empty primary). See clarification

   - **Ctx-aware iterator binding (per GPT v14 finding HIGH / v15)** —
     load-bearing for ctx propagation. The slice methods' `readFunc`
     bodies MUST build the underlying iter via `query.IterContext(ctx)`,
     NOT `query.Iter()`. Existing `ScanContext` / `MapScanContext`
     already use the context-aware driver call (`cql_client.go:2308`,
     `:2358`); the slice methods follow the same pattern.

     Why it matters: the drain helpers (`drainIterScanWithLimit`,
     `drainIterToSliceMapWithLimit`) deliberately do NOT check
     `ctx.Done()` between rows — they delegate ctx propagation to the
     iter itself. With `IterContext(ctx)`, the gocql/cassandra-gocql-driver
     v2 iter checks ctx on each page fetch and surfaces ctx errors via
     `iter.Close()` / `scanner.Err()`. With plain `Iter()`, ctx
     cancellation would be invisible to the iterator, and a long
     drain on a cancelled ctx would continue running until natural
     exhaustion — silently violating the public `*Context` method's
     contract. The plan's ctx-error semantics tests
     (`TestExecuteFallbackRead_CtxCanceled_PropagatesFromAlt_SliceOnly`,
     etc.) would still pass at the public-method layer because they
     drive ctx errors through synthetic readFunc returns rather than
     real driver paths.

   - **Mechanical PageState option-guard at the public method (per
     GPT v14 finding MEDIUM / v15)** — load-bearing for the four-vector
     PageState short-circuit. Phase 4 enumerates the four cluster-switching
     mechanisms PageState must bypass; phase 1 provides the wrapper-level
     plumbing (`opts.preserveSelectedCluster`, the
     `executeReadNoFailover` wrapper that gates `executeFallbackRead`
     invocation on `opts.fallbackRead`). The slice public methods MUST
     pre-derive `opts` so a single source of truth — `q.pageState != nil`
     — drives all four switches, rather than relying on every call
     site to remember every short-circuit:

     ```go
     // sliceReadOpts derives effective readOptions for the four new
     // slice methods. When q.pageState != nil, all four cluster-switching
     // mechanisms are mechanically disabled in one place:
     //   - opts.fallbackRead = false:        suppresses executeFallbackRead
     //                                       empty-retry inside the wrapper.
     //   - opts.preserveSelectedCluster:     suppresses drain-aware initial
     //                                       rerouting AND AllowedClusters
     //                                       override drain-filter fallback
     //                                       (phase 1 / GPT v9).
     //   - route through executeReadNoFailover: suppresses standard
     //                                          executeRead failover
     //                                          (returned as a flag the
     //                                          caller uses to pick which
     //                                          wrapper to invoke).
     func (q *cqlQuery) sliceReadOpts(ctx context.Context) (opts readOptions, useNoFailover bool) {
         opts = q.client.resolveReadOptions(ctx, q)
         if q.pageState != nil {
             opts.fallbackRead = false
             opts.preserveSelectedCluster = true
             return opts, true
         }
         return opts, false
     }
     ```

     Both `SliceMap*` and `SliceScan*` consume this helper so the
     short-circuit cannot drift between the two methods. `SliceScan*`
     always uses `executeReadNoFailover` regardless of the
     `useNoFailover` flag (per clarification #1); the helper still
     applies the `opts.fallbackRead = false` rule for `SliceScan +
     PageState` so the wrapper does not invoke `executeFallbackRead`
     when the primary returned 0 rows on a cursor-paged call.

     Why mechanical, not call-site-managed: the alternative — letting
     each public method call `resolveReadOptions` and then conditionally
     mutate `opts` based on `q.pageState` — is the bug-magnet pattern
     `nonHealthAltErr` was rejected for in v12. Two callers having to
     register the same predicate is a drift hazard. One helper keeps
     the rule single-sourced.

     Why NOT add a `suppressFallbackRead` field to `readOptions`
     (the alternative GPT v14 floated): it would create a second
     gating predicate path doing the same job as `opts.fallbackRead`,
     and force every wrapper site (`executeRead`, `executeReadNoFailover`)
     to consult both. Pre-deriving `opts.fallbackRead = false` reuses
     the existing wrapper contract verbatim — no new field, no new
     predicate site.

     Test additions:
     - `TestSliceMap_PageState_DerivesFallbackReadFalse` (assert that
       a `SliceMap` call with `q.pageState != nil` and chained
       `.FallbackRead()` produces an effective `opts.fallbackRead =
       false` at the wrapper boundary — proves the mechanical
       derivation, not the behavioral end-state which existing tests
       already cover)
     - `TestSliceScan_PageState_DerivesFallbackReadFalse` (companion)
   - Close/error precedence — **the two helpers use DIFFERENT deferred-close
     patterns** because the underlying gocql iter and scanner have
     asymmetric page-boundary semantics. This was caught by GPT v7
     (correctly reversing v7's earlier "use the same pattern for both"
     guidance). Verified by symbol against both supported drivers
     (pinned versions: `github.com/gocql/gocql v1.7.0` and
     `github.com/apache/cassandra-gocql-driver/v2 v2.0.0`; line numbers
     drift across patch releases and module-cache formatting and so are
     intentionally NOT cited):
     - `(*Iter).Scan` (both drivers): `*iter = *iter.next.fetch()` —
       **in-place replacement**, so the outer `iter` variable always
       points to the active page.
     - `(*iterScanner).Next` (both drivers): `is.iter = iter.next.fetch()`
       — **pointer reassignment** on the scanner's internal field. The
       outer `iter` variable is left pointing at page 1 even after the
       scanner has advanced to later pages.

     Implication: a `defer iter.Close()` on the original iter is correct
     for `SliceMap` (closes the active page because of in-place
     replacement) but **wrong for `SliceScan`** — across page boundaries
     it would close the already-drained page 1 iter while leaking the
     active later-page iter that the scanner actually owns.

     **Nil-callback guard placement** (per GPT v8 review): the
     "no cluster contact" promise in the public Godoc is mechanically
     enforced at the **public method**, NOT in the helper. By the time
     the helper has a `cql.Iter`, a session has already been selected
     and a query already executed — that's already cluster contact.
     Place the guard at the top of `cqlQuery.SliceScanContext`:

     ```go
     func (q *cqlQuery) SliceScanContext(
         ctx context.Context, scanFn func(RowScanner) error,
     ) (int, error) {
         if scanFn == nil {
             return 0, errNilSliceScanFn
         }
         opts := q.client.resolveReadOptions(ctx, q)
         // ... build readFunc that calls drainIterScanWithLimit ...
         return rowCount, q.client.executeReadNoFailover(ctx, opts, readFunc)
     }
     ```

     The same shape applies to non-context `SliceScan` (which delegates
     to `SliceScanContext` via `q.getContext()` per the existing
     `Scan`/`MapScan` convention). The helper-level guard is retained
     as defense-in-depth only — it should never fire in production
     because the public method already screened.

     **`SliceScan` helper — defer scanner.Err() (scanner owns close):**
     ```go
     func drainIterScanWithLimit(
         iter cql.Iter, max int, scanFn func(RowScanner) error,
     ) (rowCount int, err error) {
         if scanFn == nil { // defense-in-depth; public method already screened
             return 0, errNilSliceScanFn
         }
         scanner := iter.Scanner()
         defer func() {
             // scanner.Err() invalidates the scanner (sets is.iter = nil,
             // is.cols = nil, is.valid = false) and calls iter.Close() on
             // whichever page-iter the scanner currently holds — exactly
             // what we want across page boundaries. Nothing else touches
             // `scanner` after the loop exits.
             if cerr := scanner.Err(); cerr != nil && err == nil {
                 err = cerr
             }
         }()
         for scanner.Next() {
             if max > 0 && rowCount >= max {
                 return rowCount, types.ErrRowLimitExceeded
             }
             if cberr := scanFn(rowScannerAdapter{scanner}); cberr != nil {
                 return rowCount, cberr
             }
             rowCount++
         }
         return rowCount, nil // defer captures iter error via scanner.Err()
     }
     ```

     **`SliceMap` helper — defer iter.Close() (in-place replacement is
     safe). MUST return `(nil, err)` on ANY error path, not only
     overflow** (per clarification #4 — partial-buffer discard is a hard
     contract, not a stylistic preference):
     ```go
     func drainIterToSliceMapWithLimit(
         iter cql.Iter, max int,
     ) (rows []map[string]any, err error) {
         defer func() {
             if cerr := iter.Close(); cerr != nil && err == nil {
                 err = cerr
             }
             // Partial-buffer discard contract (clarification #4):
             // on ANY error — overflow, mid-drain iter error captured
             // by Close, anything — return nil rows. Prevents the
             // public method from accidentally exposing a partial
             // driver-buffered slice when the alt-error suppression
             // path translates the err to ErrNotFound and (nil, nil).
             if err != nil {
                 rows = nil
             }
         }()
         for {
             m := map[string]any{}
             if !iter.MapScan(m) {
                 break
             }
             if max > 0 && len(rows) >= max {
                 return nil, types.ErrRowLimitExceeded
             }
             rows = append(rows, m)
         }
         return rows, nil
     }
     ```

     The deferred `rows = nil` is what closes the SliceMap analog of
     GPT v10's HIGH finding: without it, a mid-drain alt error captured
     via `iter.Close()` would leave `rows` populated with a partial
     buffer that the public method's closure could still observe and
     return — and once the alt error is suppressed to `ErrNotFound`,
     the caller would see `(partialRows, nil)`. Locked by
     `TestSliceMap_AltErroredMidDrain_NoPartialRowsExposed` in the
     test plan.

     **Scope note (per advisor v11 review):** the discard contract is
     a helper-level invariant — it protects every error path that
     flows through `drainIterToSliceMapWithLimit`, not only the
     FallbackRead alt-error path that motivated the fix. In particular,
     it also closes the analogous hole on the standard-failover path
     for `SliceMap`: if the primary errors mid-drain and
     `tryFallbackCluster` reruns the readFunc on the alt with the alt
     also erroring, the public method returns `(nil, DualClusterError)`
     rather than `(partialAltRows, DualClusterError)`. Locked by
     `TestSliceMap_PrimaryMidDrainError_AltAlsoErrors_NoPartialRowsExposed`.

     Verified contract used by both helpers (symbol references; drivers
     pinned per go.mod):
     - `(*Iter).Close` is idempotent — guarded by atomic
       `CompareAndSwap` on `iter.closed`; multiple calls return the
       same `iter.err` and release framer only on the first call.
     - `(*iterScanner).Err` invalidates the scanner (`is.iter = nil`,
       etc.) and delegates to `(*Iter).Close` on whichever page-iter
       `is.iter` currently holds — which is why it's the right
       close-owner for `SliceScan`.
     - Both patterns preserve the desired precedence: `ErrRowLimitExceeded`
       and scanFn errors win over close error (the `err == nil` guard in
       the defer prevents overwrite). Only on natural exhaustion does
       close error become the returned error.

     **Helper signature uses `cql.Iter`, NOT `*gocql.Iter`.** The root
     `cql_client.go` is written against `github.com/arloliu/helix/adapter/cql`
     so both v1 and v2 driver adapters can plug in (`adapter/cql/adapter.go:195-222`).
     A concrete `*gocql.Iter` would break the v2 adapter and likely fail
     to compile in the shared root implementation.

     **Wrapped-scanFn allocation check (phase-2 implementation

3. **`MaxRows` bound + page-size clamp**
   - `cqlQuery.MaxRows(n)` + `q.maxRows *int`. Negative → panic.
     **`n >= math.MaxInt32` → panic** (per GPT v12 finding #2 —
     supersedes the v5-era `math.MaxInt` bound). Rationale: the
     page-size clamp computes `effectiveMaxRows + 1` and forwards
     the result through `query.PageSize(int)`; both pinned drivers
     (`github.com/gocql/gocql v1.7.0` and
     `github.com/apache/cassandra-gocql-driver/v2 v2.0.0`) encode
     the page size on the native CQL protocol wire as `int32`. On
     64-bit platforms, values in `[math.MaxInt32, math.MaxInt-1]`
     pass the old `< math.MaxInt` check but become negative when
     cast to `int32` for the wire — producing an invalid or wrapped
     page size at execution time and silently breaking the
     documented memory-safety bound. Tightening to
     `n < math.MaxInt32` ensures `n + 1` always fits in signed
     int32. The previous `math.MaxInt` panic case is subsumed by
     this stricter bound. Boundary spec: `n` in `[0, math.MaxInt32 - 1]`
     accepted; `n` in `(-∞, -1] ∪ [math.MaxInt32, +∞)` rejected
     (panic for per-query, option error for default).
   - `Config.DefaultMaxRows` + `WithDefaultMaxRows` option, with
     `root_validation.go` entry: non-negative AND `< math.MaxInt32`
     (returns option error for `>= math.MaxInt32`, matching the
     existing negative-value validation pattern). Same rationale as
     the per-query bound.
   - Wire the bound into both drain helpers: counted loop, abort upon
     detecting an (N+1)th row.
   - **Page-size clamp** (load-bearing for actual memory bounding): in
     the slice methods' query-build path, when `effectiveMaxRows > 0`,
     compute `clampedPageSize = effectiveMaxRows + 1` if user did not
     set `PageSize`, else `min(userPageSize, effectiveMaxRows+1)`, then
     apply via `query.PageSize(clampedPageSize)`. This bounds the
     driver's per-page fetch in addition to Helix's accumulator. Note:
     this means slice methods may NOT see the user's literal `PageSize`
     when `MaxRows` is also set. Document this clearly.
   - **Precedence with `PageState`** (per GPT v4 review): when both
     `MaxRows` and `PageState` are set on the same call, the page-size
     clamp **always wins** — i.e., the underlying
     `query.PageSize(clampedPageSize)` is applied even when paging
     through a cursor produced by an earlier call with a different
     page size. Rationale: memory safety > paging convenience. Some
     drivers tolerate cross-page page-size changes; others may behave
     oddly. Caller responsibility: when paging across multiple slice
     calls with `PageState`, keep `MaxRows` and `PageSize` stable
     across all calls so the clamp produces the same value each time.
     Document loudly in Godoc and the user guide.
   - Tests per the matrix in the test plan section, including a
     dedicated test that asserts the underlying `query.PageSize(...)`
     receives the clamped value, not just that the returned slice is
     bounded.

4. **`FallbackRead` integration**
   - Slice-method `readFunc` returns `types.ErrNotFound` when its drained
     result is empty, so `executeFallbackRead` treats empty exactly like
     a single-row scan returning `ErrNotFound`.
   - Public methods translate `ErrNotFound` from the read pipeline back
     to `(nil, nil)` / `(0, nil)`.
   - **`PageState` short-circuit (extends to ALL cross-cluster movement)**:
     when `q.pageState != nil`, slice methods bypass FOUR distinct
     cluster-switching mechanisms:
     1. **No standard `executeRead` failover** — route through
        `executeReadNoFailover` (from phase 1) instead of `executeRead`.
     2. **No `FallbackRead` empty-retry** — skip the
        `executeFallbackRead` invocation that would otherwise fire on
        empty-result.
     3. **No drain-aware initial rerouting** (per GPT v4 review).
        `executeReadNoFailover`'s primary cluster selection skips the
        drain-aware re-selection step that today swaps the selected
        cluster when it's draining. Rationale: drain-aware rerouting
        moves the cursor across clusters BEFORE any retry trigger
        fires, leaking PageState to the wrong cluster the same way
        failover would. Implementation: pass an explicit
        `readOptions.preserveSelectedCluster bool` (or equivalent
        field) that `runPrimaryRead` consults; slice methods set it to
        `true` when `q.pageState != nil`.
     4. **No `AllowedClusters` override drain-filter** (per GPT v9
        review). Today `resolveReadTarget` filters draining entries
        out of the override result and falls back to the next entry
        (`cql_client.go:1289`). For PageState slice calls, that fallback
        ships the opaque cursor to the wrong cluster. Fix (phase 1):
        when `opts.preserveSelectedCluster=true`, the resolver returns
        the first known override entry as-is and fails closed with
        `types.ErrNoValidClusters` if that entry is draining. The slice
        method's caller sees `ErrNoValidClusters` and can retry without
        PageState (or wait for drain to clear) — loud failure beats
        silent cursor-leak.
   - **What this does NOT solve**: read-strategy variability across
     paged calls (e.g., `RoundRobinRead` picking different clusters
     for page 1 vs page 2) is still the caller's responsibility, as
     covered in the cluster-origin caveat. v1.5.0 plugs the leaks
     Helix can plug; the rest stays caller-managed.
   - Tests per the matrix in the test plan section, including a new
     test where the selected cluster is draining + `pageState != nil`
     → the alt session must NOT be contacted.

5. **Drain-aware alt skip + slice-aware alt-error propagation**

See clarification #5

   - `Scan` / `MapScan` call sites pass `fallbackReadOptions{}` (zero

     `nonHealthAltErr` nil → record health on all real errors).
   - **`SliceMap` call sites** pass:
     ```go
     fallbackReadOptions{

         },

             return errors.Is(err, context.Canceled) ||
                 errors.Is(err, context.DeadlineExceeded)

     ```
     `SliceMap` does not need a "callback was invoked" clause for
     `propagateAltErr` because its partial-buffer discard contract
     (clarification #4 Shape B) ensures that suppressing a real alt
     error to `ErrNotFound` cannot expose partial rows.

   - **`SliceScan` call sites** pass a closure that captures a
     `scanFnInvokedOnAlt bool` flag set via a wrapped `scanFn`
     (per GPT v11 review — supersedes v11's `rowCount > 0` proxy
     because `rowCount` is **successful callbacks only**, while the
     propagation decision needs "callback was invoked at all,
     including invocations that returned an error". See
     clarification #4 Shape A "Why not `rowCount > 0`".):
     ```go
     var rowCount int           // successful callbacks only
     var scanFnInvokedOnAlt bool // set inside wrapped scanFn before calling user scanFn
     readFunc := func(ctx context.Context, sess cql.Session) error {
         query := sess.Query(q.statement, q.values...)
         query = q.applyConfig(query) // includes PageState + page-size clamp
         iter := query.IterContext(ctx) // ctx-aware (GPT v14 HIGH / v15)
         wrapped := func(r RowScanner) error {
             scanFnInvokedOnAlt = true
             return scanFn(r)
         }
         n, err := drainIterScanWithLimit(iter, max, wrapped)
         rowCount = n
         return err
     }
     fallbackOpts := fallbackReadOptions{
         skipDrainingAlt: true,
         propagateAltErr: func(err error) bool {
             // Propagate when scanFn was invoked at all on the alt
             // drain — covers BOTH the partial-mutation-then-iter-err
             // case AND the scanFn-returned-error-on-first-row case.
             // Without the second, the public API contract that
             // scanFn errors propagate would be violated when alt's
             // first row's scanFn returned an error.
             if scanFnInvokedOnAlt {
                 return true
             }
             return errors.Is(err, types.ErrRowLimitExceeded) ||
                 errors.Is(err, context.Canceled) ||
                 errors.Is(err, context.DeadlineExceeded)
         },
         nonHealthAltErr: func(err error) bool {
             // Caller-driven errors only (clarification #5).
             // ErrRowLimitExceeded already handled by
             // isReadTerminalNonHealth.
             // Note: scanFn-returned errors record health (real iter
             // errors and decoder errors are not distinguished in
             // v1.5.0; see clarification #5 closing paragraph).
             return errors.Is(err, context.Canceled) ||
                 errors.Is(err, context.DeadlineExceeded)
         },
     }
     ```
     Sequencing is safe: `executeFallbackRead` invokes the alt's
     `readFunc` synchronously and only evaluates `propagateAltErr`
     and `nonHealthAltErr` after `readFunc` returns. The closure
     variables are consistent at evaluation time — no atomic needed.

     **Health classification (refined v12 → v13 per GPT v12 finding #1).**
     For a real alt error (not `ErrNotFound`, not `ErrRowLimitExceeded`):
     - If `nonHealthAltErr(err)` returns true → skip `IncReadError`,
       `recordOpOutcome`, AND `RecordFailure` on alt. The propagation
       decision (governed by `propagateAltErr`) still applies
       independently — caller may still see the error.
     - Otherwise → record health on alt as today.
     `ErrRowLimitExceeded` is already health-skipped at the alt path
     by `isReadTerminalNonHealth` (phase 1, layered above
     `nonHealthAltErr`).

     **Primary-readFunc reuse note.** The same `readFunc` (and
     therefore the same `wrapped`) is invoked twice — first against
     the primary by `runPrimaryRead`, then against the alt by
     `executeFallbackRead`. The flag is shared via closure capture.
     This is safe because the only path that reaches
     `propagateAltErr` is "primary returned 0 rows → ErrNotFound →
     fallback" — and an empty primary drain never enters
     `drainIterScanWithLimit`'s `for scanner.Next()` loop, so
     `scanFnInvokedOnAlt` cannot be set on the primary leg. By the
     time the predicate runs, the flag reflects the alt drain
     exclusively.
   - **Drain-skip return semantics (load-bearing for telemetry hygiene)**:
     when `skipDrainingAlt` triggers, `executeFallbackRead` returns
     `types.ErrNotFound` to its caller without:
     - contacting the alt session
     - emitting `IncReadTotal` / `ObserveReadDuration` for the alt
     - emitting `IncReadDivergence` (the alt was never probed, so we
       don't know if it diverged)
     - emitting `IncReadError` or calling `RecordFailure` on the alt
       (skipping is a routing decision, not a fault)

     Slice public methods translate the resulting `ErrNotFound` to
     `(nil, nil)` / `(0, nil)` as usual.
   - **Scope of ctx-error special handling**: ctx-error propagation
     AND health-skip are BOTH scoped to alt errors during slice
     fallback. Propagation is governed by `propagateAltErr`;
     health-skip by `nonHealthAltErr` (per GPT v12 finding #1 /
     clarification #5). Neither applies to:
     - Primary ctx errors anywhere — they remain real cluster errors
       and trigger `IncReadError` + `RecordFailure` (cluster slowness
       or unreachability is a real signal worth recording on the
       primary path; the slice-specific exception is for the
       FallbackRead alt leg only).
     - `Scan` / `MapScan` alt ctx errors — they keep current
       suppression-and-record-health behavior (preserves existing
       API contract; slice methods deliberately diverge).
     - **`SliceMap` alt ctx errors during executeRead's standard
       failover** (`tryFallbackCluster` / `executeNormalFailover` /
       `executeOverrideFailover`). The slice-specific exception is
       FallbackRead-only — standard failover deliberately keeps
       today's "alt ctx err records health" behavior, even for
       `SliceMap`. Rationale: in FallbackRead empty-retry, primary
       returned 0 rows successfully and the caller is most likely
       cancelling because they got their answer; recording alt
       ctx-err as a cluster fault would be a false positive. In
       standard failover, primary already FAILED with a real error;
       if alt also returns ctx-err under the same deadline that just
       killed primary, both clusters were genuinely slow — that IS
       cluster signal worth recording. The asymmetry is deliberate
       and behavior-equivalent to today's `Scan` standard-failover
       semantics. (Per Opus 4.7 v14 → v15 self-review.)
     - Single-cluster mode reads — unaffected.
   - Tests: alt-draining behavior diverges between `Scan` (bypass) and
     slice (skip); alt ctx errors propagate for slice but suppress for
     `Scan`; alt ctx errors **do NOT advance health for slice** but
     **DO record health for `Scan`** (regression preserves today's
     `Scan` behavior — see test list); row-limit propagates for
     slice; non-ctx non-row-limit alt errors continue to suppress for
     both AND continue to record health for both; primary ctx errors
     still poison health for both `Scan` and slice methods (regression
     test); drain-skip emits no alt metrics and does not contact the
     alt session.

Proposed by Gemini v2 as a way to handle the success-path silent
corruption case for `SliceScan` under standard failover. Rejected in
favor of **no standard failover for `SliceScan`** (clarification #1).

Reasons:

- `resetFn` clutters the API for the common case where standard failover
  doesn't fire.
- Doesn't generalize to `scanFn` implementations that emit to channels,
  write to a DB, or push to other external sinks where "reset" has no
  clean meaning.
- Easy to forget to wire and silently broken when omitted — the safety
  property becomes a caller obligation rather than a library guarantee.
- The library still needs the same "no failover after first callback"
  internal decision to know when to invoke `resetFn`. The no-failover
  rule is a strict simplification of the resetFn design with the same
  safety guarantee and a smaller API surface.

Callers that need cross-cluster retry on real cluster errors should use
`SliceMap` (which buffers driver-side and is safe to retry) or catch the
error from `SliceScan` and retry the whole call themselves with a fresh
accumulator.

### "scanFn must be idempotent" documentation contract (Gemini v2 Option B)

Proposed as a documentation-only path: tell callers their `scanFn` must
be idempotent under retry. Rejected.

Reasons:

- The natural shape — `append(slice, row)` — is not idempotent. Most
  callers will write this and not realize the contract is broken.
- A documentation contract that the natural code path silently violates
  is worse than no contract at all. Loud failure (no auto-failover) is
  safer than silent corruption (auto-failover with idempotence
  assumption).
- Idempotence-via-keyed-upsert (e.g., `m[id] = row`) works but forces
  every caller to allocate a map for use cases where a slice is the
  natural shape.

### Helix-owned typed-value buffer for `SliceScan` (GPT v2 alternate)

Proposed: buffer rows into Helix-owned typed values, replay through user
callbacks once at end of drain. Rejected.

Reasons:

- Reopens the destination-shape problem the streaming-callback contract
  intentionally avoids: Helix would need to know the user's destination
  types ahead of drain, which requires either reflection metadata
  (out-of-scope per non-goals) or losing gocql's destination-driven
  unmarshalling path.
- The whole reason `SliceScan` exists (vs. just walking `SliceMap`'s
  output) is preserving custom `UnmarshalCQL` and other type-aware
  unmarshalling. A typed-value buffer that loses this is strictly worse
  than telling callers to use `SliceMap`.

### `SliceScanAs[T]` returning partial accumulator on error — RESOLVED in v5

Original conflict (v4): Gemini's review described the partial-on-error
return as "Mechanically Sound" and a positive trait that "matches the
documented 'undefined state on error' contract". GPT v4 took the opposite
position and recommended `nil, err` always. **Picked GPT v4's position.**

**Resolution (v5):** Gemini v5 reviewed the pushback and explicitly
reversed their v4 implicit endorsement, calling the `nil, err` decision
"a superior architectural decision" that "completely eliminates the
risk of an application accidentally processing corrupted partial rows".
Both reviewers now agree. Disagreement entry retained for historical
context but no longer active.

Reasons (visible to future Gemini reviews):

- `SliceScanAs` exists as the *safe convenience layer* — the
  most-ergonomic typed-slice API. Convenience helpers should not
  propagate the underlying primitive's footgun-y contract to their
  most ergonomic surface; that defeats the purpose of layering.
- Standard Go convention for value+error returns is to return the
  zero value when err != nil (`json.Unmarshal`, `os.ReadFile`,
  `io.ReadAll`, etc.). Following the convention reduces surprise.
- "If you need partial state, use `SliceScan` directly" is a clean
  separation. Callers who consciously want the accumulator can always
  drop down one layer.
- Append-to-slice is the natural shape inside the helper's `decode`
  callback, and the natural shape for the helper's caller is "I get a
  slice OR an error". Returning partial slices invites callers to
  process them, which is the exact error mode we documented as
  undefined for `SliceScan`. Returning nil makes the misuse impossible.

The underlying `SliceScan` keeps its current `(rowCount, err)` shape
where rowCount may be nonzero on err — that contract is unchanged.
Only the convenience helper diverges.
